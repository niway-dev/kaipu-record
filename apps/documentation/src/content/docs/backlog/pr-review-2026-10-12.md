## The conclusion

Nothing reviewed lets one user touch another user's data. But **four deploy prerequisites
would take production down** if missed, **two PRs are blocked**, and several PRs depend on each
other: merged in the wrong order they break things, in the right order they fix each other.

### #268: every path that deletes data, and its condition

1. `sweepExpiredReservations` — `status='reserved'` and `ticket_expires_at < now − 3 h`, ≤ 50/tick; claim first, a confirm that wins the race makes it a no-op.
2. `retryPendingDeletes` — `status='deleting'`, ≤ 50/tick, idempotent (404 = success).
3. `finalizeDueAccountDeletions` — `DELETE FROM user WHERE id = $1 AND EXISTS(account_deletion with scheduled_at <= now)`, ≤ 10/tick; a restore that lands first makes it a no-op.
4. `purgeAccountObjects` — keys under `videos/<userId>/` and `img/<userId>/` (trailing slash: `user1` ≠ `user10`), only when no `user` row exists, `attempts < 10`, ≤ 5 jobs and 200 deletes/tick.
5. `requestAccountDeletion` — deletes the caller's sessions only.
6. `restoreAccount` — deletes the caller's `account_deletion` row.

The cron is not reachable over HTTP in production (`--test-scheduled` is dev-only). No
cross-user deletion path found.

## Cross-cutting findings (already on `main`, not introduced by these PRs)

- **Vault ids are not validated** in desktop IPC: `rename` and `screenshotSave` (`overwriteId`)
  already accept `../`; #245 adds a third. One fix in the vault: ids must match
  `/^[A-Za-z0-9_-]+$/` and exist before any write. Deserves its own PR.
- **The legacy upload endpoint** skips quota and verification (fixed by #276).
- **SSR may serialize the whole Better Auth session**, `session.token` included, into the HTML
  via `_authenticated` `beforeLoad` (PLAUSIBLE). Check: view source of any authenticated page.
- **Cookie is `SameSite=none` and `/api/v1/*` has no Origin check** (fixed by #278).
