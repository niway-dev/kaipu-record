# R2 storage architecture (public vs private content)

> **Status: 🔵 Proposed** — captured while wiring desktop distribution. Needed before the
> upload features (videos / images) ship, so private content isn't exposed.

## What we want

A home for everything the product stores, with **per-content access rules**:

| Content                                       | Access                              |
| --------------------------------------------- | ----------------------------------- |
| App installers (desktop DMGs + update feed)   | **Public** (anyone clicks download) |
| Uploaded videos                               | **Private** (per-user, not public)  |
| Uploaded images                               | **Private** (per-user)              |
| Web-app images (used by the marketing/app UI) | "Public, but only from our app"     |

## The R2 reality (why "one bucket, mixed folders" doesn't work)

- **R2 public access is at the BUCKET level, not per-folder.** Connecting a custom domain
  (`updates.kaipu.app`) makes the **entire** bucket publicly readable. You cannot mark some
  prefixes public and others private through the public domain.
- "Folders" in R2 are just **key prefixes** (`download/`, `videos/`, …) — they carry no
  permissions of their own.

So a single public bucket with mixed public/private folders is **not possible**. Today
`kaipu-bucket` is public via `updates.kaipu.app` — fine for installers, but **private content must
not live in it as-is** (it would be reachable by URL).

## Two viable architectures

### Option A — Private bucket(s) + a Worker gateway (recommended)

Keep the bucket(s) **private** (no public domain). A Cloudflare Worker with an **R2 binding** serves
every object, enforcing rules per request:

- `GET /download/...` → anyone (installers).
- `GET /videos/<id>` → check the user's session; 403 otherwise.
- `GET /img/<id>` → public-web images, optionally same-origin/referer-checked.

Pros: full per-path / per-user / per-file control, one place for rules, can stream + cache.
Cons: a small Worker to build and maintain.

### Option B — Split buckets

- **`kaipu-bucket`** (public, via `updates.kaipu.app`) → only public content: **installers +
  public web images**.
- **`kaipu-private`** (private, no public domain) → **videos + private images**, served via the
  Worker or time-limited **presigned URLs** generated by the API.

Pros: simplest mental model (public bucket = public). Cons: still needs a Worker / presigned-URL
path for the private bucket; two buckets to manage.

## On "public images, but only from our app"

For images the browser loads, you can't truly restrict to "only our app" without a token — the
browser still makes the request and `Referer` is spoofable. Practical answers:

- Serve them **through the app's Worker** (same-origin under `kaipu.app`), so access goes through
  code you control, or
- Accept they're publicly cacheable (most web images are) and just keep them in the public bucket.

## Decision (chosen): split buckets

Going with **Option B (split buckets)**:

| Bucket                 | Public access | Custom domain       | Holds                                  |
| ---------------------- | ------------- | ------------------- | -------------------------------------- |
| `kaipu-bucket`         | **ON**        | `updates.kaipu.app` | installers, update feed, public assets |
| `kaipu-private-bucket` | **OFF**       | **none**            | uploaded videos, private images        |

**Hard rule: the private bucket gets NO custom domain.** A custom domain on R2 makes the whole
bucket publicly readable — attaching one to `kaipu-private-bucket` would defeat its purpose. Keep
its Public Access **disabled** and no domain.

Private content is read **through code**, never a public URL:

- a Worker with an R2 binding (`env.PRIVATE_BUCKET.get(key)`) that checks the user's session before
  serving, or
- short-lived **presigned URLs** generated by the API.

That Worker / presigned-URL path is built when the upload features (videos/images) land. For now,
only `kaipu-bucket` (public, distribution) is in use.

## Key layout per bucket

`kaipu-bucket` (public):

```
download/latest/…            # installers (CI-managed)
download/<version>/…         # versioned installers
updates/…                    # electron-updater feed
version-gate.json            # version gate config
web/…                        # public web-app assets
```

`kaipu-private-bucket` (private — read via Worker/presigned only):

```
videos/<userId>/<id>         # user recordings
img/<userId>/<id>            # user images
```
