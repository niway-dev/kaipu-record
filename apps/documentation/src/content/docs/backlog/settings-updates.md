# Settings → Updates

> **Status: 🔵 Design written, not implemented** (2026-09-24). Owner report: "I just
> published an update, several minutes passed and nothing happens. I assume it has not
> downloaded it yet or is waiting for some action." Parent:
> [auto-update](./auto-update) (shipped) · [settings roadmap](./settings-roadmap).
>
> **The design lives in [Settings → Updates — design](../specs/2026-09-24-settings-updates-design).**
> This page keeps the problem statement; the spec holds the decisions.

## What happens today, and why "nothing happens"

`main/updater/auto-updater.ts` is wired and the feed works — on 2026-09-23
`https://updates.kaipu.app/updates/latest-mac.yml` served `0.7.0` minutes after the
release job finished. What the owner hit is the design, not a bug:

1. **The check runs once at launch, then every 6 hours.** An app that was already open
   when the release landed will not look again for up to six hours. There is no check on
   focus, no manual trigger.
2. **Only one state is visible.** `UpdateStatus` is `idle | ready`. The renderer hears
   nothing for _checking_, _update available_, _downloading_ (a ~125 MB zip), _up to
   date_ or _error_ — the first and only signal is the "restart to update" banner after
   the download completes. Between the check and that banner the app looks idle.
3. **Dev builds never check.** `if (!app.isPackaged) return;` — running from `bun run dev`
   will never see an update. Worth remembering when testing.

So "waiting for some action" is exactly right: it is waiting for the next 6-hour tick,
and even when it does act, nothing shows until the download is done.

The deeper mismatch: Kaipu is a **menu-bar resident app, meant to stay open for days**.
"Check at launch" is the wrong primary trigger for something that rarely launches. The
manual button and the focus-throttled check are the paths that will actually run; the
6-hour timer is the fallback, not the design.

## Proposal

An **Updates** section on the Settings → App page.

> **Cut on 2026-09-24:** this proposal originally included an `Automatic updates` toggle
> persisted in `AppSettings.autoUpdate`. The owner removed it: "I want a button to look
> for changes, not to enable or disable updates — I don't want them disabled." Automatic
> background updates stay mandatory and have no off switch.

| Row                    | Content                                                                                                             |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **Version**            | `Kaipu Record 0.7.0` · channel (`stable`) · "Last checked 3 min ago".                                               |
| **Status + action**    | One line that follows the updater state, with the matching button — see the table below.                            |
| **Release notes** link | The GitHub release page for the available/installed version (the changelog is already generated by release-please). |

State → copy → button:

| `UpdateStatus.state`           | Copy                                         | Button                  |
| ------------------------------ | -------------------------------------------- | ----------------------- |
| `idle` / `up-to-date`          | "You're on the latest version."              | **Check for updates**   |
| `checking`                     | "Checking…"                                  | disabled                |
| `available` (autoDownload off) | "Version 0.7.0 is available."                | **Download**            |
| `downloading`                  | "Downloading 0.7.0 — 43 %"                   | disabled, progress bar  |
| `ready`                        | "0.7.0 is ready to install."                 | **Restart and install** |
| `error`                        | "Couldn't check for updates." + short reason | **Try again**           |

The existing "restart" banner keeps working; it is the same `ready` state rendered
elsewhere.

### Changes

- **`UpdateStatus`** grows to the full state machine above, plus `checkedAt` and a
  `progress` for `downloading` (`electron-updater` emits `checking-for-update`,
  `update-available`, `update-not-available`, `download-progress`, `update-downloaded`,
  `error` — every state already exists as an event; today four of them are dropped).
- **Two IPC calls**: `updater:check` (calls `checkForUpdates()`, returns the resulting
  status) and `updater:install` (exists as `installDownloadedUpdate`). Status keeps
  flowing through the existing `updateStatus` push so every window agrees.
- **`checkForUpdates()` is re-entrant-unsafe** in electron-updater while a download is in
  flight; the handler must ignore a manual check during `downloading` rather than start a
  second one.
- **Cadence**: keep 6 hours, add a check on window focus throttled to once per 30 minutes
  (the version gate already uses this throttle pattern; reuse it).
- **Dev builds**: the page should say "Updates are disabled in development builds" instead
  of a dead button, so nobody debugs a no-op.

## Non-goals

- Channels (`beta`) and downgrades — the feed is single-channel today.
- Replacing the version gate. The gate is the fail-open kill-switch that works without
  the updater; this page is the updater's face. They already share the "restart" banner.

## Acceptance

- [ ] With an older build installed and a newer version on the feed, **Check for updates**
      goes checking → downloading (progress moves) → ready, and **Restart and install**
      installs it. No 6-hour wait.
- [ ] On the latest version, the button reports "You're on the latest version" with the
      checked-at time.
- [ ] Feed unreachable (airplane mode): the error copy shows, **Try again** works when
      back online; nothing throws.
- [ ] A manual check while a download is in flight does not start a second download.
- [ ] `bun run dev`: the section explains updates are off in dev.
