## Context

Today the desktop app has exactly one library folder. `vault-location.ts` keeps one
`vaultDirectory` string in `userData/preferences.json` and falls back to `Videos/Kaipu Record`;
`currentVault()` builds a `LibraryVault` for that path on every call. Changing the folder in
Settings → Files only changes which folder is listed.

The owner records for work and for personal use and wants the two kept apart. The goal is
**separation**: a leak of work captures (a shared screen showing the Library, a folder sent
to someone, a cloud listing) must never include personal ones, and the reverse. Decided with
the owner on 2026-10-29 (Linear NIW2-370).

The user-facing word is **workspace**. "Vault" survives only in existing code identifiers.

## Decision

1. **A workspace is an existing folder** the user picks. Kaipu initializes it by writing
   `.kaipu/workspace.json` (`version`, a UUID `id`, a display `name`, `createdAt`, a `color`
   from the tag palette and optional `initials`). The folder is
   never created by Kaipu, and Kaipu never creates the folder root again once it is registered:
   a missing root means "unavailable", not "empty".
2. **A folder that already has `.kaipu/` is adopted**: its `workspace.json` is reused, or
   minted when absent (a vault from before this ADR). Its sidecars, tags and edit projects are
   used as they are. The vault that exists at the first launch after the upgrade becomes the
   first workspace and is named **"Default workspace"**, not after its folder, because the
   folder's name ("Kaipu Record") says nothing and "Personal" would presume what it holds. A
   workspace the user adds later defaults to its folder's name, which the add dialog lets them
   change.
3. **The list lives in userData**: `preferences.json` gains a `workspaces` object with the
   registered entries (id, path, cached name) and `activeId`. The folder holds the identity;
   userData holds which folders this machine knows and which one is active.
4. **One active workspace.** The Library, the editors, tags and every new capture work on the
   active workspace only. There is no combined view and no per-capture destination. "All
   workspaces" exists only as the Settings scope for defaults (ADR 0034), never as a Library
   view. The switcher is a stack of tiles in the navigation rail, and one click switches. The
   active workspace is named wherever a capture or a write is about to land (spec, UI).
   **None of this depends on the number of workspaces.** With one workspace the rail still shows
   the active tile and a "+" tile, the status bar still shows the chip, and a one-time,
   dismissible hint ("New: workspaces — keep work and personal captures apart") shows after the
   upgrade and is remembered in userData. The "Move to" menus offer "New workspace…" when no other
   workspace exists. Only what needs a choice (the Settings scope selector, the tray submenu,
   the ⌘digit switch, the window-title prefix) waits for a second workspace.
5. **Switching is refused while anything writes into the active workspace**: a recording, an
   export, a GIF save, a screenshot save, or a move. Each writer also binds its folder when it
   starts, so a write always ends in the workspace it started in.
6. **Item addresses carry the workspace, and main serves only the active one.** Every IPC call
   that names an item, and every tag-registry call, sends `workspaceId` and the **workspace
   generation** it was made under. Main runs the call only when both match the active
   workspace, and binds the resolved folder once for the whole operation (a repository
   operation never resolves the folder twice). A stale call is rejected with `stale-workspace`
   and writes nothing. The mover and the startup sweeps are the only code that touches a
   non-active workspace, and they are main-internal.
7. **A switch is a transaction, not a flag.** `workspaces:switch` runs these steps in order, and
   stops at the first that fails, leaving the old workspace active:
   1. Refuse if a writer is busy (decision 5).
   2. Main enters `switching`: new item-scoped calls are rejected, and calls already running
      are drained (every call runs inside a per-workspace gate, so the switch awaits them).
   3. Every renderer window is asked to prepare. Editors **flush and await their pending
      saves**. An editor with unsaved changes asks Save, Discard or Cancel; Cancel aborts the
      switch. The screenshot editor, the video editor and the item detail page are closed and
      unmounted. Media and thumbnail caches and the list queries are cleared.
   4. Pending quiet-capture toasts are dismissed and their retained bytes dropped (decision 9).
   5. Main bumps the generation, sets `activeId` and persists it, then broadcasts
      `workspaces:changed` with the new generation. Renderers reload their lists.
      A response that arrives after the switch carries the old generation and is discarded by the
      renderer. Nothing from the old workspace stays mounted, so there is no editor left to copy
      pixels to the clipboard or to save.
8. **A workspace whose folder cannot be reached is unavailable**: it is listed, cannot be
   switched to, cannot receive a move, and is never silently replaced by another one. If the
   active workspace becomes unavailable, captures are refused with a message. They do not fall
   back to another workspace. A `workspace.json` that exists but is evicted by a sync provider
   (dataless) does **not** make the workspace unavailable: the registry's id is used until the
   file can be read, and moves into it wait for that read (spec, Synced folders).
9. **A capture is bound to a workspace when it starts.** The capture request resolves the
   active `workspaceId` once. That id travels with the retained bytes, the toast payload, the
   toast's Save and Annotate actions and the editor source, and the save resolves the folder
   from it. If it is not the active workspace any more when an action arrives, the action
   writes nothing. The switch (decision 7) drops the retained bytes, so a delayed click can
   never land in the new workspace. A quiet capture is copy-only, so its pixels are already on
   the clipboard when the bytes are dropped.
10. **A workspace may live in a folder a sync provider manages** (Google Drive, OneDrive,
    iCloud Drive through macOS File Provider). Kaipu detects it by path, says so, keeps its
    scratch files (recording staging, drag copies) outside the folder, and treats an evicted
    file as "in the cloud", never as missing. It adds no provider integration (spec, Synced
    folders).
11. **Tags stay per workspace** (ADR 0020 unchanged). **The cloud catalog stays per account**,
    and every cloud asset records the `workspaceId` it belongs to. A workspace's Library hides
    cloud entries of other workspaces. Hiding is a view: it never removes other workspaces'
    entries from the account cache. The cloud entries of a **deleted** workspace stay on the
    server and are hidden in every Library. Settings → Workspaces lists them ("N cloud items are
    not in any workspace on this Mac") with **Assign to workspace…**, one explicit choice. They
    are never assigned automatically, which would be the leak this ADR prevents.

## Alternatives rejected

- **One combined Library with a workspace filter** (Lightroom's folders inside one catalog, an
  "All" view). Separation becomes a filter: a cleared filter, a search that ignores it, or a
  bug in one query shows everything on a shared screen. Every surface (search, tags, the
  Editor home, counts) would have to remember the filter. The goal is that the other workspace
  is not loaded at all. This also covers an "All workspaces" Library sorted by time, which the
  owner raised on 2026-10-29 and declined on 2026-10-30 (spec, decision 24). "All workspaces"
  exists only as the Settings scope for defaults.
- **Hiding the feature until a second workspace exists** (the first draft). A user with one
  workspace would never learn that workspaces exist, so the owner asked for the tile, the chip
  and a hint from the first launch. The cost is a little extra chrome for users who never add
  one; the hint is shown once and the tiles take one 36 px slot.
- **A destination picker on every capture.** It adds a decision to every capture, and a wrong
  click is the exact leak this exists to prevent. Quiet capture (ADR 0024) has no place to
  ask.
- **A registry inside each folder only, no list in userData.** The app cannot discover folders
  it does not know. Something on the machine has to list them, and userData is where
  `vaultDirectory` already lives.
- **The path as the workspace's identity** (no `workspace.json`). Renaming or moving the
  folder, a drive mounted under another name, or a second machine would make it a different
  workspace. The cloud `workspaceId` would then point at nothing. A copied folder could not be
  told apart from a moved one.
- **A separate app profile per workspace** (separate userData, like browser profiles). This
  splits settings, the signed-in account and shortcuts, and needs a relaunch to switch. That
  is too heavy for "keep these files apart".

## Consequences

- `vault-location.ts` becomes a workspace registry: list, add/adopt, switch, rename, remove.
  `currentVault()` callers that act on a named item resolve by `workspaceId` instead.
- Main gains a per-workspace operation gate and a generation counter. The renderer stamps
  calls with both, and the switch drains the gate. This is what makes "one active workspace"
  true for an editor that was already open, not just for the next call.
- `kaipu-media://` URLs carry the workspace id, so a URL the renderer cached before a switch
  cannot resolve an item with the same id in another folder.
- The startup sweeps run for every available workspace: stranded-take recovery
  (`main/index.ts:1006`) and drag-copy cleanup (`main/index.ts:713`, `:1144`). Today they run
  for the active vault only.
- The cloud gains one server field (`cloud_asset.workspace_id`) and one endpoint to change it.
  Desktop upload has not shipped yet (no client calls `/assets/upload-intents`), so in practice
  no cloud row exists without a workspace.
- Tag sync (ADR 0021, not implemented) merges by slug "in the account". Under this ADR it must
  merge per workspace, or work tag names would appear in the personal workspace. 0021 needs an
  amendment before NIW2-368 is built.
- A copied workspace folder adopted on the same machine arrives with an id that is already
  registered. The copy gets a new id, and its items keep their `assetId`s, so their cloud
  entries stay with the original.
- `preferences.json` keeps writing `vaultDirectory`, set to the active path, **on every
  switch** and with no end date, so any older version opens the workspace that was active.
  Retiring it needs a later ADR. An older version that changes the folder writes only
  `vaultDirectory` and keeps the `workspaces` key (`vault-location.ts:70-80` spreads the file it
  read), so the next launch of this version adopts that folder and makes it active (spec,
  Migration).
- Settings stay one app-wide level that a workspace can override for five keys (ADR 0034). This
  replaces the non-goal "settings … per workspace" that this ADR listed before the 2026-10-29
  amendment.
- The one-time hint is remembered in userData (`workspaces.hintDismissedAt` in
  `preferences.json`), not in the folder: it is about this install. An older version keeps the
  key with the rest of the `workspaces` object.
- `.kaipu/workspace.json` and `.kaipu/settings.json` are reserved names, like `tags.json`. A
  media file whose stem is `workspace`, `settings` or `tags` must never address them as its
  sidecar (spec, Things the code contradicted).

## Non-goals

Renaming code from vault to workspace; search across workspaces or a combined Library view;
tags shared between workspaces; a destination per capture; syncing the workspace list between
machines; workspaces on the web dashboard; shortcuts or a Kaipu Cloud account per workspace;
an integration with a provider's API (Drive, OneDrive); locking a synced workspace that is open
on two Macs at once.

Until the 2026-10-29 amendment this list also excluded settings per workspace. That non-goal
is withdrawn: [ADR 0034](/architecture/decisions/0034-per-workspace-setting-overrides/) adds overrides for five keys.

## Reopen when

- Users need to see two workspaces at once (compare, bulk triage across them).
- Captures must be routed automatically (by app, window or schedule) instead of by the active
  workspace.
- The workspace list must follow the user to another machine, or a workspace must be shared
  with another person. A synced folder open on two Macs is supported only as "same folder, no
  locking"; real sharing reopens this.
