## Context

Until now the database schema shipped by a human running `drizzle-kit push` against
production. There were no migration files, so a schema change was not reviewable in a pull
request as SQL, not repeatable on another database, and not reversible by reading history.
The release pipeline never touched the schema, so code that needs a column could deploy
before the column existed.

The schema is about to carry more weight: foreign keys between the cloud tables, accounting
rows that quota depends on, and a purge queue that deletes customer data. A silent drift
between what the code expects and what production holds is now an availability and a
data-retention risk.

## Decision

- Schema changes are **versioned SQL migrations committed in
  `packages/infra-db/src/migrations/`**, generated by `drizzle-kit generate` from the schema
  files in `packages/infra-db/src/schema/`. The migration and the schema change land in the
  same pull request.
- `0000_baseline.sql` represents the production schema as it was on `main` before this
  decision. `0001_integrity.sql` carries the first real change (foreign keys on the cloud
  tables, a dropped duplicate index, defaults on two auth timestamps).
- `db:push` stops being the way schema changes ship. `db:generate` and `db:migrate` are the
  commands; `db:check` verifies that no schema change lacks its migration.
- CI runs `bun run db:check` in the `lint` job of `pr-checks.yml`. It runs `drizzle-kit generate`
  and fails if that writes anything. It reads no database and needs no secret. Under
  [ADR 0027](/architecture/decisions/0027-verify-release-candidates-only/) that job runs on
  release candidates only, so drift is caught before a release, not on every pull request; run
  `bun run db:check` locally after any schema edit.
- `.github/CODEOWNERS` names `@csdev19` as owner of the schema, the migrations and the
  drizzle config, so a ruleset that requires code-owner review gates them.
- **Applying a migration to production stays a manual, owner-run step** (`bun run db:migrate`
  against the production URL). It is deliberately not part of the release workflows yet.

## Alternatives rejected

- **Keep `db:push`.** Fast, and fine for a throwaway database. Rejected for production: it
  diffs the live database at run time, so what it executes is decided on the operator's
  machine and was never reviewed. It can also drop data to make the database match.
- **Run `db:migrate` inside the release workflows now.** It closes the "code deployed before
  the column" gap, but it gives CI a production database credential and makes a bad migration
  an automatic outage. Rejected until a migration has been applied by hand once and the owner
  has decided how to gate the step (a protected GitHub environment is the likely shape).
- **Regenerate the baseline from the live database with `drizzle-kit pull`.** That records
  what production happens to be, including any accidental drift, as the intended schema.
  Rejected: the baseline is the schema in the repository, and a difference found while
  marking it applied is a bug to fix, not a fact to bless.
- **A different migration tool (Atlas, Flyway, dbmate).** Better rollback and linting
  stories, but a second source of truth next to the Drizzle schema the code already imports.
  Not worth the translation layer at this size.

## Consequences

- Every schema change is reviewable SQL, in order, in the repository.
- Drizzle migrations are forward-only. There is no `down`; undoing a change means writing a
  new migration. Review the SQL, not only the schema diff.
- The drizzle journal (`drizzle.__drizzle_migrations` in the production database) becomes
  part of production state. Until the baseline is marked as applied there, running
  `db:migrate` against production would try to create tables that already exist and fail.
- A migration that fails halfway can leave the database partly changed if it holds several
  statements that are not individually safe to repeat. Keep migrations small and prefer
  additive steps.
- `0001_integrity.sql` adds a foreign key from `cloud_revision` to `cloud_asset` and one from
  `cloud_asset.current_revision_id` to `cloud_revision`. If production holds a revision with
  no matching asset, applying it fails. The owner pre-check below finds such rows.

## Non-goals

- Automated rollback or down-migrations.
- Applying migrations from CI or on deploy (the next step, once the first manual run is done).
- Changing timestamp types or adding CHECK constraints on the free-text status columns — those
  need a data migration and are tracked in the [technical-debt ledger](/backlog/technical-debt/).
- A staging database or per-PR databases.

## Reopen when

- A migration needs to run on every deploy because manual application has caused (or nearly
  caused) a code-before-schema outage.
- A second person or a second environment needs to apply migrations, so the owner-only step
  no longer fits.
- Drizzle's forward-only model blocks a needed change that a down-migration would make safe.

## Owner procedure: mark the baseline as applied on production

Do this **once**, before the first `db:migrate` against production. The baseline describes
tables that already exist, so it must be recorded as applied without being run. Rehearse the
whole procedure on a Neon branch of production first (a copy-on-write snapshot, zero risk),
then repeat it on production.

1. **Check production matches the baseline.** With the production URL (see
   [Commands](/commands/) for the inline `DATABASE_URL` convention), run
   `drizzle-kit push --strict --verbose` from `packages/infra-db`, read the statements it
   prints, then **answer no / abort**. `--strict` is what makes this a read-only check: without
   it, `push` applies non-destructive statements immediately and only asks about data loss.
   The expected list is exactly the statements of `0001_integrity.sql` and nothing else.
   Anything else is drift: stop and reconcile it in the schema first.
2. **Check for orphan rows** (they block the new foreign keys). Both queries must return no rows:

   ```sql
   SELECT r.revision_id
   FROM kaipu_record_cloud_revision r
   LEFT JOIN kaipu_record_cloud_asset a
     ON a.user_id = r.user_id AND a.asset_id = r.asset_id
   WHERE a.asset_id IS NULL;

   SELECT a.user_id, a.asset_id
   FROM kaipu_record_cloud_asset a
   LEFT JOIN kaipu_record_cloud_revision r ON r.revision_id = a.current_revision_id
   WHERE a.current_revision_id IS NOT NULL AND r.revision_id IS NULL;
   ```

3. **Record the baseline in the drizzle journal.** Drizzle decides what to run by comparing
   each migration's journal timestamp with the newest `created_at` in the table, so inserting
   the baseline row is what makes it "applied":

   ```sql
   CREATE SCHEMA IF NOT EXISTS drizzle;
   CREATE TABLE IF NOT EXISTS drizzle.__drizzle_migrations (
     id SERIAL PRIMARY KEY,
     hash text NOT NULL,
     created_at bigint
   );
   INSERT INTO drizzle.__drizzle_migrations (hash, created_at)
   VALUES ('a020c8d2c44757eea1ef404a4719e9b2f3d46df3a55d5f014a3586efc259a9fe', 1791782508821);
   ```

   The hash is the SHA-256 of `0000_baseline.sql`
   (`shasum -a 256 packages/infra-db/src/migrations/0000_baseline.sql`); `created_at` is the
   `when` value of the `0000_baseline` entry in `meta/_journal.json`. Do not regenerate the
   baseline afterwards: its timestamp would change.

4. **Apply the rest:** `bun run db:migrate` against production applies `0001_integrity.sql`.
5. **Verify:** `SELECT count(*) FROM drizzle.__drizzle_migrations;` returns 2, and
   `bun run db:check` stays green on `main`.

A fresh database (development, a new environment) needs none of this: `bun run db:migrate`
applies `0000` and `0001` in order.
