# ADR 0026: Zod is the only environment schema; no varlock, no .env.example

## Context

Since [#345](https://github.com/niway-dev/kaipu-record/pull/345), `bun env:pull` generates every
local `.env` from Infisical, and nothing else contacts Infisical in development. Nobody copies a
`.env.example` to fill it in any more; the four that exist (`server-hono`, `web-hono`, `console`,
`kaipu-record`) are documentation only, and they already drift: `server-hono`'s lacks
`RESEND_API_KEY`, `AUTH_EMAIL_FROM` and `PUBLIC_WEB_URL`.

Three places describe the same variables: the Zod schemas in `@kaipu/infra-env` (executable,
validated at start-up), the `.env.example` files (prose, never checked) and the inventory in
[Secrets layout](/deployment/secrets-layout/) (folders and tags, never checked either).

varlock was considered as the replacement for the examples, a second time:

- **2026-09-18**, as a full migration (PRs #112, #113). Set aside: the schemas already exist in
  Zod, and Cloudflare Workers need two fragile runtime integrations. Recorded in the hub page
  [varlock: evaluated, not the default](https://github.com/csdev19/general-knowledge/blob/main/infra/varlock-evaluation.md).
- **2026-10-19**, in validate-only mode: a committed `.env.schema` checked by `varlock load`,
  with no resolvers. That removes the runtime integrations but keeps a second schema beside Zod,
  which still guards production, where values never pass through a developer's machine. Its
  redaction of sensitive values covers only varlock's own output; it would not have stopped the
  2026-10-19 incident, where an agent printed `infisical export` output into a transcript.

## Decision

1. **The Zod schemas in `@kaipu/infra-env` are the only executable description of the
   environment.** Apps validate through `parseEnv` (from #345). `apps/console` gets a schema,
   `consoleEnvSchema`, for the four variables it reads.
2. **The `.env.example` files of the four apps are deleted.** The generated `.env` is the
   working file; the inventory is the description.
3. **The inventory in `deployment/secrets-layout.md` is the human documentation of every
   variable.** It gains a column for what each variable is for and what happens when it is
   missing, carrying over what the deleted examples explained.
4. **A test fails when a key of any Zod schema is absent from the inventory.** The direction is
   schema → inventory: code cannot read a variable nobody documented.
5. **varlock is not adopted**, in any mode.

## Alternatives rejected

- **varlock as a CLI validator, Zod kept at runtime.** Replaces the examples with an executable
  file, but two schemas describe each variable and need their own drift test. The hub page's first
  reason against varlock, a duplicate of a working Zod schema, applies unchanged.
- **varlock replacing Zod.** One schema, generated types, leak scanning; but it needs varlock's
  runtime integrations for Vite, both Cloudflare Worker shapes and electron-vite, which is what
  stopped the September migration. It also stops being validate-only.
- **Generate `.env.example` from the Zod schemas.** Keeps a file people recognise, but it is a
  third copy produced from the first, and the comments that make the examples useful cannot be
  generated.
- **Keep the examples by hand.** The current state: three descriptions, none checked against the
  others.

## Consequences

- One executable schema and one prose description, joined by a test, instead of three unchecked
  copies.
- A new variable means: add it to the Zod schema (if the app validates), to Infisical with a tag,
  and to the inventory; the test enforces the last step.
- `kaipu-record` stays without a schema: every variable there is optional and the app degrades
  without it by design. The inventory alone describes them, unchecked.
- A contributor without Infisical access has no template to fill in. Today PRs are limited to
  collaborators who have that access.
- Leak prevention stays outside the repo: an agent-side hook that refuses commands printing secret
  values. It is not a project decision and is not recorded here.

## Non-goals

- Validating production values on a developer machine; Zod at Worker start-up stays the guard.
- A schema for `kaipu-record`.
- Changing CI, deploy or signing (`.env.signing.example` stays).
- Generated TypeScript types for the environment beyond what `z.output` already gives.

## What would reopen this

- A secret ends up in a client bundle or a production log — varlock's leak detection is then worth
  its cost.
- A contributor without Infisical access needs to run the stack — a template becomes necessary.
- varlock documents an offline-safe cache and a single integration for every runtime here — the
  runtime cost behind the September decision disappears.
