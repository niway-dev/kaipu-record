## Context

The owner wants subtitles and a transcript of each recording, made on the user's machine. The
owner already runs NVIDIA Parakeet TDT 0.6B v3 (int8) in invisible-assistant, through the
sherpa-onnx v1.13.8 prebuilt package, and measured it ahead of Whisper on Spanish there (4.54% vs
6.91% WER on FLEURS es_419, about a third of the latency;
[research](/backlog/local-transcription/3-invisible-assistant-prior-art/)).

Facts this decision rests on:

- **The Node addon fails inside Electron.** `sherpa-onnx-node` throws "External buffers are not
  allowed", in a utilityProcess too
  ([hub: local speech-to-text](https://github.com/csdev19/general-knowledge/blob/main/desktop/local-speech-to-text.md)).
  The engine has to be a separate process.
- **The websocket server opens a network port on every interface.** On 2026-11-15 on the owner's
  M5, `sherpa-onnx-offline-websocket-server` accepts only `--port` and lsof showed it
  listening on `*:<port>`. The invisible-assistant notes say it exits on a malformed payload.
- **The batch CLI works on the same files.** On the same machine, `sherpa-onnx-offline` with the
  v3 int8 model transcribed two short TTS clips (English and Spanish, 12.4 s) word-perfect with
  punctuation, in 1.78 s wall time including model load (RTF 0.025, peak RSS 1.24 GB). It prints
  one JSON line per input file with `text`, `tokens`, `timestamps`, `durations` and
  `ys_log_probs`.
- **The model is ~640 MB** (encoder, decoder, joiner, tokens; CC-BY-4.0). The desktop installer
  today carries only small in-house Swift helpers in `resources/native/`.
- **Local-first.** ADR 0021's context states that a user without an account keeps every feature
  offline.
- **Audio decode lives in the renderer.** The app has no ffmpeg (ADR 0001); mediabunny decodes
  through WebCodecs, which exists in the renderer, not in main.

## Decision

1. **A port in main.** `SpeechRecognizer` takes a PCM file plus segments and returns tokens with
   start, duration and log-probability per segment. Main owns the job: segmentation, CLI calls,
   progress, cancel and resume. One job at a time.
2. **macOS arm64 backend: `sherpa-onnx-offline` from one pinned sherpa-onnx release**, with its
   `libonnxruntime`, shipped in `resources/native/`, asar unpacked, signed, checked by a
   `--version` handshake at startup and by the release workflow. v1.13.8 is the release verified
   on the owner's machine; v2.0.1 (October 2026) exists and M0 measured it against v1.13.8 (see M0 results); v2.0.0 was not
   measured. It reads WAV files and writes
   JSON on stdout. It opens no port. It runs under its own supervisor (deadline per batch,
   bounded stdout, kill on cancel), not the one-shot `runHelperProcess` with its 16 MB cap.
3. **The renderer decodes once.** It turns the recording's audio track into a 16 kHz mono PCM file
   in `.kaipu/tmp`, in chunks, and hands main the path. Main splits it into segments using the
   strategy M0 chooses (padding and overlap, see M0 results) and calls the CLI on batches of
   segments, so the model load (~1.5 s) is paid once per batch.
4. **A model catalog.** Each entry: id, label, languages, size, source URL, pinned revision,
   SHA-256 of every file, and capabilities (word timestamps). Two entries at first: Parakeet TDT
   0.6B v3 int8 (default, 25 European languages) and v2 int8 (English only). Whisper and others
   are later entries, not new code paths.
5. **The model is downloaded once, with consent.** The app shows size and destination before
   downloading to `userData/models/<id>/`, shows progress, allows cancel, writes to a `.partial`
   directory, checks every file's SHA-256, and renames it into place in one step. The engine loads
   only a complete, verified directory. Settings can delete it.
6. **Offline after the download, an explicit exception to local-first.** ADR 0021's context asks
   for every feature offline, forever; transcription needs one download first. From the moment the
   model is installed it works offline. Before that, the feature says what it needs and the app
   works as before. No audio leaves the machine.
7. **Elsewhere, unavailable.** Windows, Intel Mac, a missing binary or a missing model all produce
   the same "unavailable" state. Nothing crashes.
8. **Pinned and attributed.** No install script fetches anything. An explicit script
   (`bun run fetch:speech-engine`, like `rebuild:native`) downloads the sherpa-onnx release archive
   by exact version, checks its SHA-256 and copies the CLI and library into `resources/native/`;
   every packaging path calls it, `bun run setup` reports when it is missing, and a bump is a
   deliberate change with a new hash. Parakeet's CC-BY-4.0 license requires attribution: the
   model's name, NVIDIA, the license and a link appear in the download prompt, and the repository
   records them in `apps/kaipu-record/THIRD_PARTY_NOTICES.md`, as invisible-assistant does. The
   app has no screen of third-party notices. sherpa-onnx (Apache-2.0) and onnxruntime (MIT) require
   their license text to travel with the binaries. The pinned archive carries
   none of its own, so the repository keeps both texts in `apps/kaipu-record/scripts/speech-engine-licenses/`,
   the fetch script copies them into `resources/native/sherpa-onnx/licenses/` (it fails if there are
   none) and the release checks that folder in the packaged arm64 app.

## Alternatives rejected

- **The websocket server, as in invisible-assistant.** Fits live dictation; a recording is a batch.
  It listens on every interface with no flag to bind localhost, and exits on a malformed payload.
  The CLI from the same package gives the same model and the same output without a port.
- **`sherpa-onnx-node` in main or a utilityProcess.** Fails in Electron (hub page above).
- **An in-house Swift helper on Core ML / FluidAudio.** Fast on Apple Silicon, but a new runtime to
  build and maintain, macOS only, and unmeasured in this repo; the owner's working setup is
  sherpa-onnx. Reopens if the CLI's speed or memory fails M0.
- **Whisper as the default.** Worse on Spanish in the owner's measurement and slower; it remains
  a catalog entry for later.
- **The model inside the installer.** Adds ~640 MB to every download, including for people who
  never transcribe.
- **Cloud transcription.** Sends the user's audio out and needs an account; contrary to local-first.

## Consequences

- One more signed binary and a ~25 MB library in the macOS app; the release workflow checks them.
- A download feature exists in the desktop app for the first time: staging, hashes, cancel, delete.
- Transcription needs ~1.2 GB of memory while the CLI runs (probe); M0 measures long recordings.
- The renderer must stay open during decode only; after that, closing the editor does not stop
  the job.
- Mic and system audio are already mixed in one track at capture, so music or a played video is
  transcribed too. Accepted for the first version.
- Parakeet v3 returned empty text on real speech in the owner's benchmark; segments with speech
  energy and no words are recorded as unresolved, not hidden.

## Non-goals

- Live captions while recording.
- Speaker labels, translation, summaries.
- A general model manager for other AI features.

## What would reopen this

- M0 shows the CLI cannot transcribe 60 minutes within a reasonable time or memory on Apple
  Silicon, or loses words at segment boundaries no padding fixes.
- A sherpa-onnx release breaks the JSON output or drops `durations`.
- The Node addon starts working inside Electron (one process less).
- Windows becomes a target: decide whether the same CLI ships there.

## M0 results

Measured on 2026-11-15 on the owner's Apple M5 Mac (24 GB), `sherpa-onnx-offline` with Parakeet TDT
0.6B v3 int8, 4 threads. The spike script is in
`apps/kaipu-record/scripts/spikes/transcription-m0/`; it prints metrics only, and no transcript text
from a recording is committed. The 5- and 20-minute inputs are cut from one real recording; the
60-minute input is a **concatenation** (a 54-minute recording plus 6 minutes of another), because no
single 60-minute recording exists. Every figure below is one run (the renderer decode is two), taken while other work was using
the machine, so treat differences under about 10% as noise.

**Decisions M0 makes**

| Choice                              | Decision                                                                                     | Numbers behind it                                                                                                                                                                                                                                                                               |
| ----------------------------------- | -------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Segmentation                        | Fixed 30 s windows overlapping by 3 s, one cut point in each overlap, rule `midpoint-dedupe` | Twice as fast as energy VAD (RTF 0.031 vs 0.066 on 60 min, both at 8 per call), no empty-with-speech segment (energy: 3 on 60 min), and a word error on known text (9.9%) no worse than energy VAD (11.6%) or a single pass (10.7%); one synthetic passage in one run cannot separate the three |
| Batch size                          | 4 segments per CLI call                                                                      | RTF 0.033, 2.1 GB peak; 8 per call is about 10% faster (20 min: 36 s vs 40 s) but peaks at 3.0 GB, and 2 per call is slower (45 s) with 1.6 GB, so 4 is the middle                                                                                                                              |
| sherpa-onnx release                 | Stay on **v1.13.8**                                                                          | v2.0.1 gives the same speed (energy VAD, 60 min: RTF 0.064 vs 0.066), memory, word count (8454 vs 8489) and word timing; nothing to gain from a bump                                                                                                                                            |
| Silero VAD (`vad-with-offline-asr`) | Not measured                                                                                 | No fixed-window segment came back empty despite voiced audio, and the seam loss measured below is small (6 deleted words against 3 for a single pass), so there was no evidence of a problem for it to fix; words lost inside a non-empty segment are not measured                              |

**Time and memory** (v1.13.8, fixed 30 s / 3 s, batch 4)

| Audio                  | Segments | CLI wall time | Real-time factor | Peak RSS of the CLI |
| ---------------------- | -------- | ------------- | ---------------- | ------------------- |
| 5 min (batch 8)        | 11       | 9 s           | 0.030            | 3.0 GB              |
| 20 min                 | 45       | 40 s          | 0.033            | 2.1 GB              |
| 60 min (concatenation) | 134      | 126 s         | 0.035            | 2.2 GB              |

One 60-minute run with 2 segments per call took 225 s, almost twice the 4-per-call time, while other work was using the machine; it is probably noise and was not repeated. The CLI is one process, so its RSS is the process tree. A 60-minute recording transcribes in about
two minutes on this machine. Memory grows with batch size (energy VAD, 20 min: 1.3 GB at 1 segment
per call, 2.0 at 4, 2.9 at 8, 4.7 at 16, 7.3 at 32), which is why the batch stays small. A batch of
1 takes 132 s for the same 20 minutes (177 calls, decoding included), so the cost of one call is well
under the 1.5 s of the first probe, which timed cold clips.

**Boundary words.** Known text read by a speech synthesizer, so the true words are exact:

| Input                                   | Strategy                   | Inserted | Deleted | Substituted | Word error |
| --------------------------------------- | -------------------------- | -------- | ------- | ----------- | ---------- |
| English, 900 words, one continuous take | single pass (reference)    | 18       | 3       | 75          | 10.7%      |
|                                         | fixed 30 s / 3 s           | 15       | 6       | 68          | 9.9%       |
|                                         | energy VAD                 | 19       | 9       | 76          | 11.6%      |
| Spanish, 177 words                      | single pass, fixed, energy | 0        | 0       | 0           | 0%         |

Fixed windows lose three more words than one pass across 11 seams in the English passage and insert
three fewer; the substitutions are the synthesizer's identifiers and acronyms, not seams. On the
real recordings the count of identical neighbouring words under 400 ms apart (a doubled boundary
word looks like this, but so does genuine repetition) is 93 in 8,490 words at 60 minutes, against 97
for energy VAD; `midpoint-dedupe` (drop a repeated word within
250 ms that lies within 600 ms of a cut and comes from a different segment) is what every run in
this section used. **The three rules in the script (`spec`, `midpoint`, `midpoint-dedupe`) were not
compared with each other**, so nothing here shows that `midpoint-dedupe` beats the others; it is
chosen because it is the only one that removes a doubled boundary word, and M1 pins its behaviour
with unit tests (a word on a boundary appears exactly once).

**Empty results on segments with speech:** 0 with fixed windows at 5, 20 and 60 minutes; 3 with
energy VAD at 60 minutes.

**Word timing against known marks** (synthesizer, one word at a time with 350 ms gaps, English and
Spanish): the median start is 56 ms off (95th percentile 110 ms) and early on average (mean −58 ms); the median end
is 33 ms off (95th percentile 100 ms) and late on average (mean +33 ms). The spec said hand-marked words; the marks here are built by construction, not by ear, but each
is the span left after trimming samples below about −40 dBFS from the synthesizer's clip, so a
quiet onset or a fading end falls outside it. That alone can account for part of the measured
bias, so read it as an upper bound on the error, not a clean measurement. Subtitles and click-to-seek can live
with a 60 ms offset; if it shows, a fixed shift in the projection removes the bias.

**Renderer decode.** Decoding a 54-minute recording (AAC 44.1 kHz stereo, 1.12 GB) to 16 kHz mono
PCM with mediabunny in headless Chrome took 7.0 and 7.1 s on the same Apple M5 (about 460 times
faster than real time) and produced the expected 104 MB of PCM in 813 chunks of 128 KB. The
page stayed responsive: the longest gap between animation frames was 16.8 ms and no gap passed
100 ms. Peak renderer memory was about 0.98 GB and flat after the first seconds, so it does not
grow with duration: a 10.4 GB export of the same length peaked at 0.5 GB, and a 17.8-hour
near-silent recording (6.9 GB) decoded in 157 s at 0.99 GB. The 60-minute figure used for the
engine is therefore decode (about 8 s) plus the 126 s job. Not diagnosed: what holds the roughly
800 MB the renderer keeps after the PCM is freed. The build must keep one copy of `mediabunny`
in the renderer bundle: with two, `AudioSampleSink` rejects the track.

**What this does not show.** Two languages and one synthesizer say little about accented or noisy
speech; the numbers cover speed, memory, boundaries and timing, not recognition quality on the
owner's recordings. The 60-minute input is a concatenation, so its seam is a splice, not a single
take.
