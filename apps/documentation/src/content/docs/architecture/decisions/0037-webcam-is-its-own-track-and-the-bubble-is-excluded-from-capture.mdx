## Context

The webcam is a floating bubble window (`src/main/recording/camera-bubble-window.ts`) that is
deliberately not content-protected so the screen capture records it as part of the screen. The
recorder (`recorder-engine.ts`) writes one MP4 — the screen plus the mixed microphone and system
audio — and nothing else. ADR 0001 anticipated a webcam overlay "composited into a `<canvas>`
per frame" at record time; the bubble-on-screen approach shipped instead because it needed no
compositing at all.

Video editor v2 broke that bargain. Its auto-zoom crops the frame along a camera path, and the
face, being pixels of the frame, is cropped away with everything else. The owner records without
zoom to keep it. A cheap fix — re-pasting the bubble's pixels from the unzoomed frame — was
rejected as a hack: the bubble's pixels are scaled, mirrored and framed screen content, not a
source. Every product the owner compares Kaipu with (Screen Studio, Cap, Tella, Camtasia) keeps
the webcam as its own source and composes it in the editor.

Two things a later reader will ask: why a second file rather than a second track or a canvas
composite, and why the bubble is still on screen while recording if it is not in the file.

## Decision

1. **The webcam is its own file**, `.kaipu/<id>.webcam.mp4` (H.264, no audio, 1280×720 @ 30 fps,
   1080 lines only while framing is active), encoded by the **recorder renderer** with a second
   mediabunny `Output` from a second `getUserMedia` stream, written through a second
   `RecordingWriter` session and moved into the vault by the same `recordingFinalize`. The file is
   raw: no mirror, no framing crop. A webcam that cannot be opened, or that ends mid-take, never
   fails the take.
2. **Sync is one clock plus a stored offset.** Both outputs are stamped from the same renderer
   `performance.now()`; `startOffsetMs = webcamT0 − screenT0` and its quality
   (`exact | estimated`, from `waitForFirstMediaTimestamp`) are stored on the sidecar under
   `webcam`, beside the recorded layout, size and fps. Pause and resume act on both sources in the
   same call. `bun run webcam-track:check` reports the offset like `cursor-track:check` reports
   the track.
3. **The bubble is excluded from the capture and stays on screen.** Plan A is the chosen path
   (owner, 2026-10-30); Plan B is recorded as the fallback and is not scheduled. Plan A: the bubble window is
   content-protected **from creation**, always — the capture path is Electron's `desktopCapturer`
   (`chromeMediaSource: "desktop"`), where Electron's Chromium patch passes in-process
   `NSWindowSharingNone` windows to ScreenCaptureKit's `initWithDisplay:excludingWindows:`, and
   Windows uses `WDA_EXCLUDEFROMCAPTURE` (10 2004+). A one-day spike with written pass/fail
   criteria (spec task 0) runs before any other work. Plan B, built only if the spike fails on a
   supported macOS: a native ScreenCaptureKit capture behind the engine's source seam that
   excludes the bubble by its window id, as Cap does, under the repo's native-dependencies rules
   (no install scripts, explicit rebuild, degrade to the Chromium path when missing). Taking it
   needs its own ticket and an amendment to this ADR.
4. **The screen file stays screen-only.** `<id>.mp4` is the original (ADR 0003) and has no face
   in it; the webcam is composed by the editor, every export and Share (ADR 0038). A recording
   without `webcam` on its sidecar — every recording made before this — is unchanged.
5. **Vault rules follow the cursor track's**, with one difference: `remove` deletes the webcam
   file, rename moves it with the id, and `removeLocalCopy` is **refused** while it exists, because
   the file is media the cloud does not carry yet (plan 03), not metadata it can drop.

## Alternatives rejected

- **Hide the bubble during the take.** Exclusion for free and on every platform, and the first
  thing that comes to mind. Rejected by the owner: the bubble exists so the user sees their
  framing while recording, and the screen must still be recorded correctly; "if Cap could, we
  can". Recorded here so it is not proposed again.
- **A second video track in the same MP4.** mediabunny writes it and keeps the tracks on one
  timeline. But the library player, QuickTime, Finder and every recipient show only the first
  track; the "original" would carry the face even when the user hides it; and every vault
  operation that reads the file would need to know about the track. Not verified how current
  players behave, and not worth finding out.
- **Composite the webcam in the recording compositor** (ADR 0001's stated path, the hub's
  "Cámara PiP"). The same burned-in pixels by another route; the zoom problem stays.
- **Encode in the bubble's renderer**, which already holds the stream. A second clock to align,
  a window that is destroyed when the camera is turned off, and an encoder in a transparent
  always-on-top panel. The recorder renderer already owns every encoder, the pause/stop order and
  the error path.
- **Re-time the tracks afterwards** by audio cross-correlation (Cap's `sync_calibration`). No
  audio on the webcam file, and one clock makes it unnecessary.
- **Native capture first.** Rejected as the default by the precedent of ADR 0022 and ADR 0030:
  the Chromium path with content protection is what the control bar and the shade already use;
  a native module is the fallback, not the plan.

## Consequences

- One more device open, one more encoder and one more file per take with the webcam on. The
  measured cost (CPU, dropped frames on the screen track) goes on the QA sheet; the Mac mini and
  the Windows beta machine are the floor.
- `RecordingWriter` sessions gain a `kind`; `recordingCreate`, `recordingWrite`, `recordingStat`
  and the stranded-recordings salvage treat the pair as one take. The IPC contract doc changes.
- The sidecar gains `webcam`; `LocalRecording.webcam` exposes it; `kaipu-media://webcam/<id>`
  serves the file.
- The bubble's comment, the hub's media-pipeline page and the capture modes spec's decision 6
  ("recorded as part of the screen, no content protection") are now wrong and say so with a
  pointer here. Decision 6's anchoring of the bubble inside a recorded area may stay as UX; it
  is no longer required for the video.
- ADR 0001's negative consequence "webcam overlay must be re-implemented by compositing into a
  canvas" is amended: the webcam is composed at preview and export time, in the editor's
  composer, not at record time.
- If Plan B is taken, it reopens the native-binding precedent of ADR 0022 and 0030 for the
  recorder on macOS only, for a reason those ADRs did not weigh (window exclusion, not cropping),
  and gets its own amendment and ticket. The Windows path stays Chromium either way.
- The terminal-line patch hypothesis ([backlog](/backlog/bug-control-bar-hides-last-terminal-line/))
  is settled by the same spike.

## Non-goals

- Uploading the webcam file (cloud plan 03).
- Audio on the webcam file; camera-only or split-screen scenes; background removal.
- Changing how the bubble is positioned, sized or dragged.
- Linux.

## Reopen when

- The spike, or a later macOS, shows content protection no longer excludes in-process windows
  from the app's own capture: then Plan B is executed and this ADR is amended with the module.
- A camera-only scene or a multi-segment project needs more than one webcam file per recording,
  or a layout that the editor cannot express over a single raw track — then a project folder
  (Cap's `content/segments/`) replaces the sidecar-plus-file pair.
- The cloud carries the webcam file: lift the `removeLocalCopy` refusal and revisit decision 5.
