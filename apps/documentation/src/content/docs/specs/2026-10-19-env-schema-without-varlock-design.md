# Environment schema without varlock — design

**Status: 🔵 Proposed · 2026-10-19.** Decisions approved by Cristian in chat on 2026-10-19;
implementation not started. ADR: [0026](/architecture/decisions/0026-zod-is-the-env-schema-no-varlock/).
Linear: NIW2-478. Builds on [#345](https://github.com/niway-dev/kaipu-record/pull/345)
(`bun env:pull`), which must merge first.

## Summary (one minute)

Every local `.env` is now generated by `bun env:pull`, so the four `.env.example` files are no
longer copied by anyone and only drift. They are deleted. What they explained moves into the
variable inventory in [Secrets layout](/deployment/secrets-layout/), which becomes the one human
description of every variable. The Zod schemas in `@kaipu/infra-env` stay the only executable
one; `console`, which reads its four variables by hand today, gets a schema too. A unit test reads
the inventory and fails when any schema key is missing from it, so code cannot start reading an
undocumented variable. varlock was evaluated again, in validate-only mode, and is not adopted: it
would be a second schema beside Zod, and its redaction would not have prevented the leak that
started this discussion.

| #   | Decision                                                                      | Why                                                                                       | ADR        |
| --- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- | ---------- |
| 1   | Zod in `@kaipu/infra-env` is the only executable env schema                   | It already validates `server-hono` and `web-hono` at start-up and in production           | 0026 (new) |
| 2   | `console` gets `consoleEnvSchema`, parsed with `parseEnv`                     | Its four variables are read by hand with silent fallbacks today                           | 0026 (new) |
| 3   | Delete the four `.env.example` files                                          | `bun env:pull` generates the real files; the examples are unchecked prose that drifts     | 0026 (new) |
| 4   | The inventory in `secrets-layout.md` gains "Purpose" and "If missing" columns | Carries over what the examples explained, in the one place already listing every variable | 0026 (new) |
| 5   | A test fails when a schema key is absent from the inventory                   | Keeps the prose honest without generating it                                              | 0026 (new) |
| 6   | No varlock                                                                    | A second schema beside Zod; runtime integrations were the September blocker               | 0026 (new) |
| 7   | `kaipu-record` stays without a schema                                         | Every variable is optional and the app degrades by design                                 | —          |
| 8   | `.env.signing.example` stays                                                  | Signing is out of scope and its file is consumed by a different flow                      | —          |

## Open questions

- **`console`'s `DATABASE_URL` becomes required.** Today a missing value falls back to `""` and
  fails later at the first query. Default: required (`min(1)`), so it fails at start-up with the
  `bun env:pull` hint. The other three keep their current defaults
  (`CONSOLE_API_URL` → `http://localhost:3000`, `CONSOLE_ENVIRONMENT` → `Unspecified`,
  `CONSOLE_ADMIN_USER_IDS` → empty, which denies everyone).
- **Where the inventory test lives.** Default: `packages/infra-env/src/inventory.test.ts`, reading
  the Markdown file by path. It couples a package test to a docs file; the alternative, a root
  script in `verify`, is one more moving part.

## Out of scope

- varlock, in any mode.
- A schema for `kaipu-record`.
- Validating production values locally; Zod at Worker start-up remains the guard.
- CI, deploy, signing and the release workflows.
- Agent-side leak prevention (a user-level Claude Code hook), which lives outside the repo.

## Failures this must protect against

Input for the tests.

1. A key is added to a Zod schema and not to the inventory → the inventory test fails, naming the
   key and the schema.
2. The inventory test passes vacuously because it parsed no table (renamed heading, moved file) →
   it asserts that it found at least one key per known schema before comparing.
3. `console` starts without `DATABASE_URL` → start-up fails with `parseEnv`'s message, naming the
   variable and `bun env:pull`, and never printing a value.
4. `console` starts without the three optional variables → same defaults as today, no error.
5. A deleted `.env.example` is still referenced by docs or code → `git grep "\.env\.example"`
   returns only `.gitignore`, `.env.signing.example` and dated specs or plans (historical records,
   left as they are).
6. A `.env.example` is committed again by habit → nothing stops it; accepted, and the inventory
   test does not care. Not worth a guard.

## Detail

### Current state (verified 2026-10-19 on `chore/env-pull-local-dotenv`)

| Consumer       | Schema                                     | `.env.example`          | Read by                                               |
| -------------- | ------------------------------------------ | ----------------------- | ----------------------------------------------------- |
| `server-hono`  | `serverEnvSchema`                          | yes, drifted            | `parseEnv(serverEnvSchema, cfEnv)`                    |
| `web-hono`     | `webServerEnvSchema`, `webClientEnvSchema` | yes                     | `parseEnv(...)` in `src/env/`                         |
| `console`      | none                                       | yes                     | `consoleConfig()` in `lib/backend.server.ts`, by hand |
| `kaipu-record` | none                                       | yes, the most commented | `import.meta.env` at each read site, all optional     |

Of the schema keys, only `AUTH_EMAIL_FROM` is missing from the inventory today; the first run of
the test will flag it.

### `consoleEnvSchema`

In `packages/infra-env/src/console.ts`, exported from the index:

```ts
// Illustrative; the implementation PR settles the exact shape.
export const consoleEnvSchema = z.object({
  DATABASE_URL: z.string().min(1),
  CONSOLE_ADMIN_USER_IDS: z.string().default(""),
  CONSOLE_API_URL: z.string().url().default("http://localhost:3000"),
  CONSOLE_ENVIRONMENT: z.string().default("Unspecified"),
});
```

`consoleConfig()` keeps merging Worker bindings over `process.env`, then parses the merged object
once with `parseEnv`. Its return shape (`databaseUrl`, `adminIds`, `apiUrl`, `environment`) does
not change, so callers are untouched.

### Inventory columns

The "Complete map — `dev`" table goes from `Secret | Folder | Tags` to
`Variable | Folder | Tags | Purpose | If missing`. The prose in the deleted examples moves into
those two columns: for instance, that `VITE_SERVER_URL` needs a scheme because the proxy calls
`fetch()` on it, that `BETTER_AUTH_URL` is the web origin without a trailing slash, and that
`kaipu-record`'s PostHog keys are public and the app runs offline without them. The column header
renames "Secret" to "Variable" because most rows are not secrets.

### Inventory test

```ts
// Illustrative.
const inventory = readFileSync(resolve(repoRoot, INVENTORY_PATH), "utf8");
const documented = new Set([...inventory.matchAll(/^\| `([A-Z][A-Z0-9_]+)`/gm)].map((m) => m[1]));

for (const [name, schema] of Object.entries(SCHEMAS)) {
  const keys = Object.keys(schema.shape);
  expect(keys.length).toBeGreaterThan(0);
  expect(keys.filter((key) => !documented.has(key)), `${name} keys missing from the inventory`).toEqual([]);
}
```

`SCHEMAS` lists every exported schema explicitly, so a new schema that is not added there is a
review question, not a silent gap.

### Files deleted

`apps/server-hono/.env.example`, `apps/web-hono/.env.example`, `apps/console/.env.example`,
`apps/kaipu-record/.env.example`. The `!.env.example` exception in `.gitignore` stays for
`.env.signing.example` and for other repos created from this template.

### Docs touched

- `deployment/secrets-layout.md` — the new columns.
- `backend/environment-variables.mdx` — one rule: a new variable goes into the schema, Infisical
  and the inventory, and the test enforces the inventory.
- `CLAUDE.md` "Secrets: Infisical" — the same rule, one line.
- The hub page `infra/varlock-evaluation.md` — a dated line recording the second evaluation and
  its reason, through the hub's own update procedure.
