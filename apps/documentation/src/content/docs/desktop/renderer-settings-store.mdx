# Renderer settings store

Every renderer window reads the app settings through one module,
`apps/kaipu-record/src/renderer/src/features/settings/settings-store.ts`. The decision and its
alternatives are in [ADR 0063](/architecture/decisions/0063-renderer-settings-are-read-through-one-store-per-window/).

## How it works

- **One read.** The store makes the window's only `window.electronAPI.getSettings()` call at
  startup. Until it lands the value is `null`.
- **One listener.** The store makes the window's only `window.electronAPI.onSettingsChanged`
  call, and keeps that listener for the window's lifetime. Main sends the full effective
  `AppSettings` on every change, so each broadcast replaces the stored value.
- **Lazy start.** Nothing touches main until the first `subscribeSettings`, `loadSettings`,
  `watchSettings`, `useSettings` or `updateSettings`.
- **Consumers are a `Set`.** Hooks and modules subscribing and unsubscribing never reach the
  bridge, so the number of `ipcRenderer` listeners does not depend on how many hooks read
  settings.
- **A broadcast before the first read wins.** It is newer than what the read saw, so the late
  read is dropped.
- **Writes.** `updateSettings(patch)` calls main and returns the new settings. Main broadcasts to
  every window, this one included, before it replies, so the broadcast normally updates the
  consumers first. The answer is published only when nothing newer landed meanwhile, so a late
  answer never rolls the window back.
- **No null flash.** A window that already holds the settings returns them on the first render.

| Export                            | Use it for                                                                                     |
| --------------------------------- | ---------------------------------------------------------------------------------------------- |
| `useSettings(selector, isEqual?)` | A React component or hook; returns the picked value, or `null` before the first read           |
| `watchSettings(listener)`         | An effect that applies settings to something outside React: called now if held, then on change |
| `subscribeSettings(listener)`     | The same, without the call for the value already held                                          |
| `getSettingsSnapshot()`           | A synchronous read of what the window holds now (`null` before the first read)                 |
| `loadSettings()`                  | A promise for the settings once the window has them                                            |
| `updateSettings(patch)`           | Writing a setting                                                                              |

## Who reads the settings

`apps/kaipu-record/src/renderer/src/features/settings/settings-consumers.ts` lists every file that
reads the store, the windows it runs in, the `AppSettings` keys it reads, whether it follows
changes live or reads once, and where a change of its keys is shown to reach it. That file is the
only list: this page does not repeat it.

Two tests keep it true:

- `settings-consumers.test.ts` scans the renderer. It fails when a file imports the store (or
  `useAppSettings`) and is missing from the map, and when a listed file no longer reads the store.
- `settings-consumers.behaviour.test.tsx` fails when a listed consumer has no behaviour case. For
  a `live` consumer, the case changes its key in a fake main process, broadcasts it, and asserts
  what the consumer returned or rendered. For a `once` one, it asserts the first read applied and
  that a later broadcast did not change it.

A consumer whose entry points at another test (`coveredIn`) is covered less directly. The scan
test checks that the test file exists and contains the names listed in `mentions`; it does not run
a broadcast through the consumer. For the pages that read through `useAppSettings`, the hook's own
test shows the hook follows a broadcast, and the scan test fails if such a file stops using the
hook or reads once with `getSettingsSnapshot` or `loadSettings`. A page that keeps the hook but
ignores a key is not caught.

`e2e/settings-listeners.e2e.ts` checks the same thing against the built app: no
`MaxListenersExceededWarning` on Record or after ten laps through the app, a change made in the
main window reaching an open capture panel, and a workspace override in force when the window opens.

## Add a consumer

```tsx
import type { AppSettings } from "@shared/types";
import { useSettings } from "@renderer/features/settings/settings-store";

// A module-level function, so its identity is stable across renders.
const pickCountdown = (settings: AppSettings): number => settings.recordingCountdownSeconds;

export function CountdownHint(): React.JSX.Element | null {
  const seconds = useSettings(pickCountdown); // null until the window has its settings
  return seconds === null ? null : <p>{seconds} s</p>;
}
```

The selector must pick a value that already exists in the settings, not build a new object or
array: a fresh object looks changed on every read. Derive anything fresh with `useMemo` from the
picked value. Main sends a new object for every field on each broadcast, so a nested pick is a new
reference each time; pass an `isEqual` function to ignore broadcasts that left it as it was
(`useShortcutLabels` does).

Outside React, `watchSettings(apply)` in an effect (or at module level) does the same and returns
the unsubscribe.

## What to watch

These are the ways the settings can go wrong without the test of any single feature noticing. The
map and the tests in [Who reads the settings](#who-reads-the-settings) are the guard; the
points below say what they do not cover.

1. **Every main path that changes settings must broadcast.** A window learns of a change only from
   main's `settings:changed` message. `updateAppSettings` and `notifyOverridesChanged` broadcast;
   a new write path that changes the effective settings without calling `broadcastSettings()`
   leaves every open window showing the old value until it is reopened. The startup path is the
   one that looks suspicious and is not: `setOverridesSource()` recomputes the effective settings
   without broadcasting, but it runs before any window exists, so nothing can be stale. In
   `main/index.ts`, `await initWorkspaces()` calls it (the `setOverridesSource(...)` call in
   `initWorkspaceSettings()`, which `initWorkspaces()` awaits, in `main/workspaces/index.ts`),
   then `registerSettings()` loads the file, recomputes the effective settings
   (`recomputeEffective()`) and registers the `settings:get` handler
   (`infrastructure/settings-store.ts`), and the first window is created after that (the
   `createWindow()` call in the `app.whenReady()` callback, before the tray and the capture panel
   are created). A renderer
   cannot read settings before the overrides source is in place. The e2e test "a workspace
   override is in force when the window opens" opens the Cloud page and checks its save-mode
   radio, which the window renders from its own store. Run on a build where the window's first read
   returns the All level's value (a stale copy), it fails: the radio shows "local-only". It does
   not fail for every reorder: `setOverridesSource()` recomputes the effective settings whenever it
   runs, so swapping `initWorkspaces()` and `registerSettings()` alone is not seen, only a window
   that reads before both. One
   path is outside this proof (read from the code, not run): a second launch that arrives after
   Electron is ready but before `registerSettings()` runs would create the main window early, and
   that window would find no `settings:get` handler. That is a failed read (point 2), not a stale
   value.
2. **A failed first read is retried only when a consumer subscribes.** The store clears the failed
   read, but nothing asks main again on a timer. A window whose first read failed stays on `null`
   until the next `subscribeSettings`, `loadSettings`, `watchSettings` or `useSettings` call
   (a route change that mounts a consumer does it). A consumer that treats `null` as final will
   show nothing for as long as it stays mounted.
3. **A consumer that reads once does not follow.** The map marks it `once` (the capture overlay's
   countdown and remembered area, the overlay's camera placeholder). That is right for a window
   that lives for one capture and wrong for one that stays open. Mark a new consumer `live`
   unless the window is short-lived.
4. **The overlay's remembered-area save merges into the window's copy.** `capture-overlay.tsx` reads
   the window's settings, replaces one display's rectangle and sends the whole object. Main's
   broadcast keeps the copy current, but two displays saving in the same few milliseconds can each
   merge into an older copy, and the later write overwrites the other display's rectangle.
5. **Selectors must return stable values.** `useSettings` runs on `useSyncExternalStore`, which
   re-renders in a loop when `getSnapshot` returns a new object on every call. A selector that
   builds an object or array needs an `isEqual` (as `useShortcutLabels` does), or must derive the
   fresh value with `useMemo` from a picked one.
6. **Module state leaks between tests unless reset.** The store lives at module level, so one
   test's value, consumers and listener would reach the next. `test/setup.ts` calls
   `resetSettingsStoreForTests()` after every test; a test that imports the store from a file
   outside that setup must do the same.
7. **Hot reload may leave an old listener (dev only, read from the code, not run).** The store has
   no `import.meta.hot` handling, so when Vite reloads `settings-store.ts` the new module opens a
   new `onSettingsChanged` listener and the old one is never unsubscribed. Each edit of that file
   during `bun run dev` adds one. Reload the window after editing the store; a packaged app never
   reloads modules.
8. **A rejected write re-reads main, and a second failure leaves the window on what it had.**
   Main merges a patch before it persists and broadcasts, so `updateSettings` can reject after
   main already holds the new value. The store then asks main what it holds (`resyncFromMain`) and
   publishes the answer unless something newer landed, then rethrows the update's own error. If
   that read fails as well, the store keeps its value and nothing says which side is right. A
   control that decides something sensitive must choose for itself: the sharing switch
   (`useShareUsagePreference`) keeps the value the user asked for until the store takes a new one.
   The re-read is skipped for an update that settles after `resetSettingsStoreForTests()`, so a
   late rejection never publishes into the next test.

## Never call `onSettingsChanged` directly

The preload opens one `ipcRenderer` listener per `onSettingsChanged` call. Node warns once a
single event holds more than ten, and a hook that subscribes for itself is how the main window
reached twelve. A test, `features/settings/settings-store-usage.test.ts`, scans the renderer source
and fails if any file other than the store mentions `onSettingsChanged`, so the count cannot creep
back up unnoticed. `features/settings/settings-store.test.ts` and the per-window count test cover
the behavior: one listener and one startup read, however many routes the main window visits.

In tests, `test/settings-ipc.ts` fakes main's side (`installSettingsIpc`), counts reads and
listeners, and broadcasts; the store resets after every test (`test/setup.ts`).

The twelve on the main window's Record page were the app's own consumers plus the Record page's
hooks, each with its own `getSettings()` on mount: about twelve reads at startup, against one now.
The consumers that read the store today are in the
[map](#who-reads-the-settings), not listed here.

The warning printed twice, not once, because StrictMode replays effects in development and the
replay resets Node's "already warned" flag.

After the change every window holds one listener and makes one startup read of its own. The
capture overlay's reads (its remembered area, countdown length and bubble size) go through
`loadSettings()`, so an overlay window makes one read too.
