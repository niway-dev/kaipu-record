# Library Vault

El modelo de datos local-first del recorder. Las grabaciones son **archivos de video en una carpeta del usuario** — no hay base de datos. El archivo de video es la fuente de verdad; la metadata vive en sidecars al lado. Esto es la implementación técnica de la filosofía en [Filesystem-First Monetization](/desktop/filesystem-first-monetization).

## Layout en disco

```
<vault>/                          (default: ~/Videos/Kaipu Record)
├── Sprint Review.mp4                          ← the media file IS the source of truth
├── Kaipu Recording 2026-10-29 at 13.51.00.mp4  ← default name of a new capture
├── Kaipu Screenshot 2026-10-29 at 13.52.10.png
└── .kaipu/                                    ← app metadata (hidden)
    ├── <id>.json                   ← sidecar: title, assetId, durationSeconds, createdAt, …
    ├── <id>.jpg                    ← poster/thumbnail (best-effort)
    ├── <id>.cursor.json            ← cursor track (recordings)
    ├── <id>.edit.json              ← video-editor session
    ├── <id>.edit.meta.json         ← session metadata
    └── <id>.assets/                ← session image assets
```

**The filename without its extension is the `id`**, and it follows the title ([ADR 0032](/architecture/decisions/0032-the-file-name-follows-the-title/)): `Sprint Review.mp4` → id = `Sprint Review`. There is no id table; the filesystem is the index. New captures are named `Kaipu <Kind> YYYY-MM-DD at HH.mm.ss` (local time; `Kind` ∈ `Recording`, `Screenshot`, `GIF`; `shared/default-capture-name.ts`), so the title and the file read the same from the start. Exports keep their derived title (`Sprint demo (YouTube)`), and the file follows it.

`LibraryVault` (`library/library-vault.ts:30`) es una clase **pura**: recibe el directorio inyectado, sin tocar `electron`. Por eso es testeable contra una carpeta temporal.

## Formato de video

`VIDEO_EXTS = [".mp4", ".webm"]`, con `.mp4` primero (`library-vault.ts:7`). Al resolver un id se prueba `.mp4` y luego `.webm`; si ninguno existe todavía, se asume `.mp4`. El `.mp4` es lo que el nuevo pipeline escribe — ver [ADR 0001: Mediabunny over FFmpeg](/architecture/decisions/0001-mediabunny-over-ffmpeg). El `.webm` queda soportado para grabaciones viejas.

## Sidecar de metadata

`.kaipu/<id>.json`, todos los campos opcionales:

```json
{ "title": "Sprint Review", "durationSeconds": 312, "createdAt": 1749938548133 }
```

`describe()` merges the sidecar with the file's `stat()` and fills defaults: without a `title` it uses `humanizeId(id)` (the stem as is; a legacy `recording-2026-10-29-13-51-00` / `screenshot-…Z` stem reads as the new default name); without `createdAt` it uses `birthtimeMs`; `durationSeconds` defaults to 0. `writeMeta()` merges (never overwrites the other fields), and it never **creates** a sidecar for an id that has neither a sidecar nor a media file (`ItemGoneError`): a hash, tag or heal write queued behind a rename cannot resurrect the old stem.

## Operaciones

| Op                                   | What it does                                                                                                                                           | Touches the media                     |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------- |
| `list()`                             | readdir → keep media exts → `describe` each → sort by `createdAt` desc                                                                                 | no                                    |
| `describe(id)`                       | `stat` + sidecar → `LocalRecording` (or `null` when there is no file)                                                                                  | no                                    |
| `allocateId(input)`                  | derive a stem from the title, resolve collisions (` (2)`, ` (3)` …), write a stub sidecar — under the `vault:names` lock. Every writer goes through it | no (the caller writes the media next) |
| `renameItem({ id, assetId }, title)` | save the title, then move the media **and every companion** to the stem the title derives; returns `{ recording, file, reason? }`                      | **yes** — the file follows the title  |
| `remove(id)`                         | delete the media + every companion (`companionPaths`: sidecar, thumbnail, cursor track, edit session, edit meta, assets)                               | yes                                   |
| `removeLocalCopy(id)`                | delete only the media; the sidecar and companions stay (cloud-only item)                                                                               | yes                                   |

`thumbnailUrl` apunta a `kaipu-media://thumb/<id>` solo si el `.jpg` existe.

## Ubicación del vault

`library/vault-location.ts` — store de preferencias minúsculo en `preferences.json` dentro de `userData` (sin dependencia `electron-store`):

- **Default**: `app.getPath("videos")/Kaipu Record`, con fallback a `~/Videos/Kaipu Record`.
- **Custom**: si el usuario eligió carpeta, se guarda en `preferences.json` y `VaultDirectory.isCustom = true`.
- `chooseVaultDirectory` abre un picker nativo; `resetVaultDirectory` borra la preferencia y vuelve al default.

Cada handler crea un `LibraryVault` fresco ligado al directorio **actual** (`currentVault()` en `library/index.ts:9`), así un cambio de carpeta aplica inmediato sin reiniciar.

## Reproducción: `kaipu-media://`

El renderer no puede leer `file://` directo (CSP + seguridad). El main expone un **esquema privilegiado streamable** (`media-protocol.ts`):

- `kaipu-media://recording/<id>` → el archivo de video, Range-aware (necesario para seek en el `<video>`). A URL is valid for the **current** id only: a rename changes it (the detail page's player reloads under the new id and keeps its position). Ids are file names derived from titles, so they can hold `#`, `?` or `%`: every URL is built with `mediaUrl(kind, id, version?)` (`shared/media-url.ts`), which percent-encodes the id; never concatenate an id into a `kaipu-media://` URL.
- `kaipu-media://thumb/<id>` → el poster `.jpg`.

`registerMediaScheme()` corre antes de `app.whenReady`; `registerMediaProtocol()` después. El handler mapea el id a su path real vía `recordingFilePath`/`thumbnailFilePath` y hace `net.fetch(file://…)`.

## Identity and sidecar v2

Sidecar v2 adds a stable identity layer (`assetId`), export provenance, lazy content hashing, and the "remove local download" operation. Fully backward compatible: v1 sidecars carry no `assetId` or `sidecarVersion`, and one is minted on first read.

### Sidecar v2 fields

All fields are optional; unknown fields are ignored:

| Field                | Type                  | Meaning                                                                                                                                                                                                                         |
| -------------------- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sidecarVersion`     | `1 \| 2`              | Omitted = v1. Set to 2 on first write of any new field.                                                                                                                                                                         |
| `assetId`            | string (UUID)         | Stable identity independent of the local filename. Minted on first read of a v1 file, persisted best-effort. Never changes, even if the file is moved or the vault is transferred.                                              |
| `derivedFromAssetId` | string \| null        | Provenance: if this recording was exported from another one, this is the source asset's id. `null` means it is original or provenance is unknown.                                                                               |
| `contentSha256`      | string (base64)       | Lazy content hash: sha256 of the media file, base64-encoded. Only present if `hashedSizeBytes` + `hashedMtimeMs` match the current file stats; otherwise stale and ignored. Computed on demand, never computed during `list()`. |
| `hashedSizeBytes`    | number                | File size when `contentSha256` was computed. Used to detect staleness.                                                                                                                                                          |
| `hashedMtimeMs`      | number                | File mtime when `contentSha256` was computed. Used to detect staleness.                                                                                                                                                         |
| `localRemovedAt`     | number (ms timestamp) | Set by `removeLocalCopy()` when the media file is deleted but identity, sidecar, and cloud relation are kept. Cleared on first read after the file reappears. Signals "cloud only" to the library.                              |
| `title`              | string                | User-facing name, exactly as typed. The file name is a sanitized projection of it (`fileStemFromTitle`); `humanizeId(id)` if omitted.                                                                                           |
| `durationSeconds`    | number                | Video duration in seconds; default 0. Backfilled by the renderer after decode on first write.                                                                                                                                   |
| `createdAt`          | number (ms timestamp) | Recording creation time; file `birthtimeMs` if omitted. Stable once set.                                                                                                                                                        |

### Lazy-mint rule for `assetId`

When a v1 sidecar (or no sidecar) is read for the first time:

1. `ensureIdentity(id)` generates a UUID and writes it to the sidecar.
2. If the vault is read-only, the id lives in memory for that process only — a read-only vault cannot persist new identities, but we do not fail to list.
3. Subsequent reads on the same machine return the persisted id.
4. If the vault is moved or the machine is replaced, the sidecar file moves with it. A different machine reading the same sidecar under a new vault path will see the same `assetId` because the file is the source of truth.

This means **every recording eventually gets an `assetId`**, even legacy ones, by first-read on any updated client.

### The filename is the local id, and it follows the title

`assetId` is the **stable cross-machine identity** (cloud catalog, routes, tags, export provenance). The **filename** is the **local working id**: `list()` enumerates it, and every companion under `.kaipu/` is found by it. Since NIW2-560 ([ADR 0032](/architecture/decisions/0032-the-file-name-follows-the-title/)) a rename moves it:

- Rename the title → `renameItem({ id, assetId }, title)` first resolves the item **by identity** under the names lock (the id when it still holds that `assetId`, else the **one** local item that does; none → `ItemNotFoundError`; more than one, of any media kind — a Finder copy made with its sidecar — → `AmbiguousIdentityError` before anything changes, shown as a plain toast; a screenshot overwrite then also requires the resolved item to be a screenshot), so a stale id never renames another item that took the name. Then the title is saved in the sidecar, and the media file and every companion move to the stem the title derives. `assetId`, tags, hash cache and provenance move with the sidecar. `LocalRecording.id` changes: treat it as valid until the next rename and never persist it.
- Title → stem (`main/library/file-stem.ts`): NFKC (no compatibility characters such as `ſ` or fullwidth letters in a file name; fullwidth `／` and `：` become the forbidden ASCII they stand for); `< > : " / \ | ? *` and control characters become spaces; dot runs collapse to one dot (so `isUnsafeId`'s `..` guard holds); leading dots and trailing dots/spaces are trimmed; Windows reserved names (`CON`, `nul`, `com1`, `Con.v2` …) get a `Kaipu ` prefix; capped at 100 code points and 180 UTF-8 bytes. Reserved stems (`isReservedStem`, compared through `fsFold` — NFKC then lower → upper → lower case — so `tagſ`, `Demo.curſor` and `ẞ`/`ß` count) are never used: a stem ending in `.edit`, `.cursor` or `.edit.meta` would have another stem's companion as its sidecar (`Demo.edit.json` is `Demo`'s edit session), so that last dot becomes a space (`Demo edit`); `tags` is `.kaipu/tags.json`, the tag registry, so it becomes `Kaipu tags`. A rename also skips any candidate whose paths overlap the source's (a legacy `Demo.edit` item renamed to `Demo`). Nothing left → the default capture name.
- Collisions → ` (2)`, ` (3)` … up to 99, then a random 4-character tail. A stem is taken when **any** media file or companion exists for it (an orphan sidecar of a cloud-only item counts). A case-only rename of the same item is a real move; the same derived stem leaves the file alone (`file: "unchanged"`).
- Order under the `vault:names` lock and the old sidecar's lock: title into the old sidecar → companions copied to the new stem → `fs.rename` of the media (the commit point) → old companions deleted. Every crash point leaves either the old item or the new item whole; a leftover is a sidecar without media whose `assetId` a live item also holds — invisible to `list()`, reused by the next rename of the same item, swept by NIW2-561.
- The OS will not let go of the file (Windows `EPERM`/`EBUSY`/`EACCES`/`ETXTBSY`) → three retries (150/400/900 ms), then `file: "kept-old-name"`, `reason: "locked"`. An export running (`exportActive`) → `"kept-old-name"`, `"busy"`, without touching the disk. The item open in the video editor → `"kept-old-name"`, `"editing"`: the editor acquires its item with `acquireEditorSession(assetId)` before it loads or writes anything; main runs the acquisition under the same names lock as renames and answers the item's **current** id, so an editor opened mid-rename waits and loads under the new id. A null answer (the item is gone) or a failed acquisition loads nothing: the editor says the item is no longer available and never falls back to the route's id, which another item may have taken. A request that waited for the lock is refused if its window closed or reloaded meanwhile (`EditorSessions` keeps a per-window generation). It releases on unmount; a window that is closed, reloaded or whose renderer crashes (`render-process-gone`) releases everything it held (`EditorSessions.watch`) (`main/library/editor-sessions.ts`). A failed companion copy → `"kept-old-name"`, `"io"`, with the new companions removed. The title is saved in every case; the renderer shows a non-blocking toast with Retry.
- Rename the `.mp4` in Finder → the id changes outside the app and the old sidecar is orphaned until reconciled (NIW2-561, not this change).
- Export a recording → the export gets its own id (named after its title) and `derivedFromAssetId` points to the original.
- Remove local download → delete the media but keep the sidecar, setting `localRemovedAt`.

If you need an identity that survives a render, reach for `assetId`. The video editor keeps its source id for its lifetime; main enforces it by refusing to move the file of an item open there (`"editing"`), whatever asks for the rename (a Library toast's Retry survives navigation).

A screenshot overwrite from the image editor goes through `LibraryVault.overwriteImage`: the check and the write happen under the names lock, and the `overwriteAssetId` the editor sends is required: an item renamed meanwhile is followed to its current id instead of having its PNG recreated under the old name, and a shot that took the old name is never overwritten. The image editor also reads its original bytes before a rename moves the file.

### Edit session metadata (`.edit.meta.json`)

When the video editor saves a project, `video-edit-session.ts` writes a sidecar:

```
.kaipu/<id>.edit.meta.json
```

```json
{
  "sourceSizeBytes": 45678900,
  "sourceMtimeMs": 1693478400000,
  "assetIds": ["<id1>", "<id2>"],
  "savedAt": 1693478500000
}
```

| Field             | Meaning                                                                    |
| ----------------- | -------------------------------------------------------------------------- |
| `sourceSizeBytes` | Size of the source video, stamped when the session is saved.               |
| `sourceMtimeMs`   | Mtime of the source video, stamped when the session is saved.              |
| `assetIds`        | The session's image assets, kept under `.kaipu/<id>.assets/<assetId>.png`. |
| `savedAt`         | Timestamp of the last project save.                                        |

The `edit-project-probe.ts` reads this to determine the editing state (see [Library](/desktop/library)): `project-available`, `needs-source`, `exported-only`, or `missing-dependencies`.

### Cloud catalog cache

When an account is signed in, `catalog-client.ts` fetches `GET /api/v1/assets` and `CatalogCache` writes it to:

```
userData/cloud/<userId>/catalog.json
```

where `<userId>` is the account id (alphanumeric, `[-_]` allowed for safety). The cache survives:

- **Vault folder moves** — the cache lives in `userData`, not the vault.
- **Vault disconnection** — unplugged drive, unsynced network folder. The cache is read-only offline; the "cloud · offline" label itself is plan 03, not this one.
- **Account switching** — each account's cache is isolated; signing out does not clear caches.

A 401 or network failure **never clears** the cache. A failed refresh leaves the previous cache intact.

### Remove local download vs Delete

Two operations, two different outcomes:

| Operation             | Deletes                                                                                                                 | Keeps                                                                                             | Use case                                                                                                                                                                                                                                                 |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `removeLocalCopy(id)` | Media file (`.mp4` / `.webm`) only                                                                                      | Sidecar (identity, hash, provenance), thumbnail, edit session, edit assets folder, cloud relation | Free disk space while preserving the cloud-linked identity. Item becomes "cloud only" and can be re-downloaded under the same `assetId`. Blocked if: no cloud copy is known, cloud copy has different bytes, hash is unknown, or an edit session exists. |
| `remove(id)`          | Media and every companion (`companionPaths`): sidecar, thumbnail, cursor track, edit session, edit meta, assets folder. | Nothing                                                                                           | Delete the entire recording permanently. Severed from the cloud.                                                                                                                                                                                         |

## Gotchas

- ⚠️ **The id is the filename, and a rename changes it.** Never persist `LocalRecording.id`, never key long-lived state by it, and patch renderer state from the rename result **by `assetId`**. A `kaipu-media://` URL is only valid for the current id.
- ⚠️ **Every new item gets its id from `vault.allocateId()`.** Picking a name yourself and writing the media races other captures and renames (`fs.rename` silently replaces an existing target on POSIX and Windows). On a write failure, `remove(id)` releases the reserved stem.
- ⚠️ A rename "kept-old-name" is not an error: the title was saved. Only an unknown id (message carries `ITEM_NOT_FOUND_MARKER`; the renderer refreshes quietly) or a title that cannot be written rejects.
- ⚠️ If the user renames the media in Finder, the id changes outside the app and the old sidecar is orphaned (NIW2-561 reconciles it).
- ⚠️ The protocol handler reads every request through `parseMediaUrl()` (`shared/media-url.ts`): it decodes the id once and answers 400 to a malformed escape or an id with `/`, `\` or `..` after decoding (`%2F` included) — the path-traversal guard. Do not bypass it.
- ⚠️ El vault directory puede cambiar en runtime; nunca cachear un `LibraryVault` de larga vida — usar `currentVault()`.
- ⚠️ Borrar es best-effort (`Promise.allSettled`): si el sidecar o thumb fallan, el video igual se borra. No tratar un fallo parcial como "no se borró nada".
- ⚠️ Windows locking behaviour (error codes under a lock, the app's own media-protocol streams not blocking a rename) is inferred from libuv and Microsoft documentation, not yet observed; the retry + `kept-old-name` path covers it either way.
