# Analytics & Feature Flags

Documenta la capa de analytics (PostHog) y feature flags del desktop. La fuente de diseño es `docs/superpowers/specs/2026-06-27-flags-and-error-handling-design.md` (archivo de diseño local, no publicado como ruta del sitio).

---

## Arquitectura: renderer-primary + main-sink

El SDK de analytics no corre en un solo lugar — se divide entre el renderer de la ventana principal y el proceso main, cada uno responsable de lo que puede observar.

### Ventana principal (renderer)

`posthog-js` se inicializa en la ventana principal (`src/renderer/src/features/analytics/posthog.ts`). Es el canal primario porque:

- Tiene acceso a `posthog-js`, que soporta feature flags y exception autocapture del renderer.
- Puede llamar a `posthog.identify(deviceId)` para asociar eventos a la instalación.
- Puede evaluar flags directamente en React con el hook `useFlag`.

### Proceso main (sink)

`posthog-node` corre en el proceso main (`src/main/services/analytics.service.ts`) como segundo canal. Sus dos roles:

1. **Crashes de Node:** captura `uncaughtException` y `unhandledRejection` del proceso main, que el renderer nunca vería.
2. **Sink IPC:** las ventanas secundarias (control-bar, camera-bubble, capture-panel) no inicializan su propio SDK. En cambio, llaman a `installCrashForwarder(origin)`, que intercepta errores del renderer y los reenvía al proceso main vía IPC `analytics:capture-exception`. El handler en `analytics-ipc.ts` los envía con `posthog-node`.

```
Ventana principal          Ventanas secundarias
  posthog-js               control-bar · camera-bubble · capture-panel
  └─ identify(deviceId)      └─ installCrashForwarder(origin)
  └─ exception autocapture       └─ IPC analytics:capture-exception
  └─ useFlag(name)                    │
                                      ▼
                           Proceso main
                             posthog-node
                             └─ uncaughtException / unhandledRejection
                             └─ sink de errores de ventanas secundarias
```

## Feature flags

### Hook `useFlag(name)`

`useFlag` (`src/renderer/src/features/analytics/use-flag.ts`) es el único punto de acceso a flags en el renderer. Internamente consulta `posthog.getFeatureFlag(name)` y devuelve el valor, o el default si el SDK no está listo, no hay key configurada, o no hay red. La app nunca lanza o se degrada por un flag indefinido.

### Flags definidos

| Flag                      | Default | In PostHog         | Purpose                                                                                                                                              |
| ------------------------- | ------- | ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `native-cursor-capture`   | `true`  | deleted 2026-11-12 | Cursor-free macOS capture with an editable cursor in the editor, for Screen, Frame and Window ([NIW2-660](https://linear.app/niway/issue/NIW2-660)). |
| `capture-while-recording` | `false` | disabled           | Screenshots during a take, macOS only (NIW2-688).                                                                                                    |
| `image-canvas`            | `false` | disabled           | Image editor canvas (NIW2-698).                                                                                                                      |
| `image-inspect`           | `false` | disabled           | Image editor Inspect mode (NIW2-699).                                                                                                                |
| `image-text`              | `false` | disabled           | Text recognition in the image editor, macOS only (NIW2-705).                                                                                         |

posthog-js (≥ 1.261.8) returns `undefined` for a **disabled** or missing flag, so the code
default applies, and `false` for an enabled flag the user does not match. A PostHog value
otherwise wins over the default.

### Turning a release flag on

`capture-while-recording` and the three `image-*` flags exist in PostHog **disabled**, so every build uses its default, `false`. To ship the feature without a release, **enable the flag at
100%**. Builds that predate the flag never read it, so they are unaffected. Once the feature is
validated, flip the default to `true` in `src/shared/analytics.ts` (or remove the flag) and
delete it from PostHog.

### Native cursor: no remote kill switch

`native-cursor-capture` was validated in production and its PostHog flag was deleted on
2026-11-12, so every build uses its own default: `true` from the release that turned it on,
`false` in 0.16.0 and earlier. To get a kill switch back, recreate the flag **disabled**, then
enable it with a 0% rollout: every build reads `false` and the next take uses Chromium capture.
Never set it to 100%: 0.16.0 and earlier ship no helper, so they would stay on Chromium and show
a developer toast on every take.

### Comportamiento offline

Si `VITE_POSTHOG_KEY` no está configurada, o si PostHog no responde, los SDKs entran en modo no-op: no envían nada y `useFlag` devuelve el default de cada flag. La app funciona exactamente igual que sin PostHog.

## Identidad por dispositivo

Al primer arranque, el settings-store acuña un `deviceId` (UUID v4) y lo persiste en `AppSettings` (`src/shared/analytics.ts`). Ese UUID es estable por instalación (no por usuario — no hay login aún).

La ventana principal llama a `posthog.identify(deviceId)` al iniciar. Dos super-propiedades se añaden a cada evento y error:

| Propiedad | Valor            | Uso                                                            |
| --------- | ---------------- | -------------------------------------------------------------- |
| `product` | `kaipu-recorder` | Filtra eventos de este producto en dashboards multi-superficie |
| `surface` | `desktop`        | Distingue desktop de futuras superficies (web, mobile)         |

## Regla de dos canales de error

`reportError(userMessage, error, { context, retry })` (`src/shared/analytics.ts`) implementa una regla estricta: el canal de usuario y el canal de desarrollador **nunca se mezclan**.

| Canal         | Qué recibe                                      | Cómo                                           |
| ------------- | ----------------------------------------------- | ---------------------------------------------- |
| Usuario       | Mensaje en español, legible, orientado a acción | Toast visible con opción Reintentar            |
| Desarrollador | Stack completo, contexto técnico, origen        | `posthog.captureException(error, { context })` |

El toast muestra solo el `userMessage` — nunca el stack, nunca el nombre de clase del error. PostHog recibe solo el payload técnico — nunca el texto que ve el usuario.

Los tres puntos de falla de grabación usan esta función:

- Falla al iniciar (`start`)
- Falla a mitad de grabación (`mid-recording`)
- Falla al finalizar (`finalize`)

Cada uno muestra un toast con **Reintentar** como acción segura (arrancar es 100% local, sin llamadas a API).

## Capa defensiva: ErrorBoundary + toast

### ErrorBoundary

Un React `ErrorBoundary` envuelve el árbol de la aplicación. Si un componente lanza una excepción no capturada:

1. Muestra un fallback amigable en lugar de pantalla en blanco.
2. Reporta la excepción a PostHog vía `posthog.captureException`.

El usuario ve un mensaje de error genérico en español, no una traza de stack.

### Primitivo `ui/toast`

`src/renderer/src/ui/toast` es el primitivo base para notificaciones en pantalla. Todas las llamadas a `reportError` pasan por acá — ninguna pantalla de error usa `alert()` o `console.error` como canal visible para el usuario.

## Privacidad

El foco en la privacidad no es opcional para una app de grabación de pantalla. La configuración de `posthog-js` desactiva explícitamente los canales invasivos:

| Capacidad               | Estado         | Motivo                                                                       |
| ----------------------- | -------------- | ---------------------------------------------------------------------------- |
| Session replay          | ❌ Desactivado | Grabaría la pantalla del usuario dentro de la app de grabación — inaceptable |
| DOM autocapture         | ❌ Desactivado | Captura texto e interacciones sin contexto — privacidad y ruido              |
| Click autocapture       | ❌ Desactivado | Idem                                                                         |
| Exception autocapture   | ✅ Activo      | Solo stacks de error — sin PII                                               |
| Feature flag evaluation | ✅ Activo      | Necesario para el comportamiento correcto de flags                           |
| Eventos explícitos      | ✅ Activo      | Solo los que el código llama explícitamente                                  |

## Pendientes (fuera de scope, documentados)

Los siguientes ítems están diseñados pero no construidos:

- **Login UI y entitlement real:** `isPaid` en `useWatermark` es un stub. El swap es una línea dentro del hook una vez que exista un plans/entitlement API. El seam ya está — nada más cambia.
- **Toggle de opt-out de telemetría en Settings:** hoy no hay forma de que el usuario desactive el envío de datos. Agregar un toggle en Settings que llame a `posthog.optOut()` / `posthog.optIn()` y persista la preferencia en `AppSettings`.
- **Eventos de producto explícitos:** la infraestructura está lista pero solo captura errores y flags hoy. Eventos como `recording_started`, `recording_completed`, o `settings_changed` se pueden agregar cuando haya necesidad analítica real.
