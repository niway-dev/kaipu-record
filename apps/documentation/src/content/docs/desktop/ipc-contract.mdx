# IPC Contract

Referencia del puente entre el proceso main y el renderer. El renderer **nunca** habla con `electron` ni con `node:*` directo — todo pasa por `window.electronAPI`, expuesto por el preload vía `contextBridge`.

## Las tres capas

```
renderer  →  window.electronAPI.foo()          (src/renderer)
          →  contextBridge bridge               (src/preload/index.ts)
          →  ipcRenderer.invoke/send → ipcMain  (canal con nombre)
          →  register*Handlers()                (src/main/*)
```

El contrato está **tipado de punta a punta** por archivos puros en `src/shared/types/` que importan ambos procesos. No hay tests de runtime del bridge: si el tipo no cuadra, no compila.

## La fuente de verdad son los tipos, no este doc

**`IPC_CHANNELS` (`shared/types/ipc.ts`) es la lista autoritativa de canales**, y `KaipuElectronAPI` (`shared/types/electron-api.ts`) es la forma completa de `window.electronAPI`. Este doc **agrupa** los canales por subsistema para orientarse; para el conteo exacto, mirá esos dos archivos (verificados por el compilador, así que no pueden desincronizarse del código). Al momento de escribir esto son ~49 canales en `IPC_CHANNELS` más 3 canales de string crudo (ver [Canales fuera del mapa](#canales-fuera-del-mapa)).

## Canales por subsistema

Dirección: **r→m** = renderer llama a main (`invoke`/`send`); **m→r** = main emite hacia el/los renderer (broadcast o dirigido).

### Settings persistidos

Sí existen y persisten: `settings-store.ts` registra ambos handlers, el preload expone `getSettings`/`updateSettings`, y `settings.json` (en `userData`) guarda theme, dock, launch-at-login, calidad de grabación, atajos y el `deviceId` de analytics.

`AppSettings.screenshotMode` (`"frame" | "window" | "screen"`, default `"frame"`; a legacy
`"area"` or any unknown stored value merges to `"frame"`) is the one current screenshot mode, shared by the
Screenshots page, the tray panel and the generic capture shortcut. Only main writes it, when a
capture completes (see § Screenshots), through `updateAppSettings(patch)` in `settings-store.ts`, the
same path as `settings:update`; no UI control writes it directly.

`settings:changed` se emite a **todas** las ventanas tras cada cambio (patrón consultar-al-montar + suscribir), para que consumidores como el hint de atajo de la barra flotante no queden stale.

Providers capture by the overlay's answer (`answer.mode`), not by the mode that was requested:
the user may have switched mode on the overlay.

After a capture main **always writes the vault first**, then applies the after-capture policy
(`decideAfterCapture(action, screenshotCopy)`). `saved` is the new vault item (`{ id, assetId }`),
`copied` says whether the clipboard got it, and `png` is an empty `ArrayBuffer` (the bytes never
cross IPC):

- **Capture** (`after: "editor"`): main also copies when `screenshotCopy` is `auto`. The renderer
  opens `/editor/image/:assetId` on the saved item, then reveals the window.
- **Copy** (`after: "quiet"`): main always copies and shows the capture toast. The renderer opens no
  editor and does not reveal the window: main already restored the pre-capture visibility.

There is no "save automatically" preference any more: every capture is in the Library, so the image
editor saves edits over that item on its own and never asks before leaving (only a pasted image, or
a capture whose vault write failed, still asks). A failed vault write is the only time the bytes cross
IPC: Capture answers `after: "editor"` with `saved: null` and the bytes, and the in-memory editor
retries the save; Copy still copies and keeps the bytes in main (`takeLastQuietCapture()`) for the
toast's Edit until the next capture starts. If a Copy manages neither to save nor to copy, main
answers `after: "editor"` with the bytes instead of losing the shot. Every screenshot vault write
broadcasts `library:changed`, so an editor already open on another item can resolve the new one.

After a quiet capture main shows the **capture toast** (`main/screenshots/capture-toast-window.ts`,
`?window=capture-toast`, `t` in the tables): one frameless, non-focusable, always-on-top window,
380 × 150 DIP, at the top-right of the work area of the display the shot came from, 18 DIP in. It
appears only after `afterCapture` has restored the windows (`beforeCapture` hides the main window
with `BrowserWindow.hide()`, never `app.hide()`), so it shows while that window stays hidden and
never brings it forward; a main window that was visible comes back with `showInactive()`, so the
app the user was in keeps the focus. `beforeCapture` also dismisses the previous toast, and the
toast window is content-protected, so it is never in the next shot. A new capture re-targets the
same window and restarts its 6 s auto-hide, counted from when the toast renderer is ready; the
pointer over the card pauses it. Edit and Open in Library ask the main window through
`screenshot:open-saved` or `screenshot:open-quiet-capture`; the renderer navigates, then calls
`revealAfterCapture()`, as on the editor path.

The global shortcut actions that feed `screenshot:hotkey` are `captureScreenshot`,
`captureScreen`, `captureFrame` and `captureWindow`, and main resolves the mode before broadcasting
(`main/screenshots/shortcut-capture.ts`). `captureScreenshot` captures with the current mode,
`AppSettings.screenshotMode`, or with `"frame"` when the platform cannot serve the stored one.
`captureScreen`, `captureFrame` and `captureWindow` open the overlay in their own mode.

**Window mode is disabled** by one flag, `WINDOW_MODE_ENABLED = false` in
`shared/types/screenshot-capture.ts` (owner decision 2026-10-18: buggy, stays off until fixed;
flip it to `true` to re-enable). The contract is unchanged: `CAPTURE_MODES` still lists
`frame`, `window`, `screen` and the `window` answer and `ListedWindow` types stay. What the
user can reach derives from `ENABLED_CAPTURE_MODES` (Frame and Screen): the overlay pill and
keys 1 and 2, the page and tray chips, `supports("window")` (false on every provider, so a
`window` request answers `unsupported`), the settings merge (a stored `"window"` reads as
`"frame"`), and main ignores a `screenshot:overlay-mode` with `"window"` and never starts the
window lister. The `captureWindow` action stays in the constants so a stored binding survives,
but it is not registered as a global shortcut and the Shortcuts page does not list it. While
enabled, Window is
served on both platforms: macOS captures by window id through `screencapture -l`, Windows through
the `desktopCapturer` window source, and both fall back to a crop of the display when the window
cannot be grabbed by id). No
shortcut writes `screenshotMode` by itself: the `screenshot:capture` handler writes it, through
`updateAppSettings` (which broadcasts `settings:changed`), from the `mode` of a `captured`
result, the mode the user ended in on the overlay. A cancelled, unsupported or failed capture
leaves it untouched, so a mode switched on the overlay and then cancelled with Esc is not
remembered. The Screenshots page and the tray panel never write it either: their Capture button
sends the current mode and each mode chip (Frame, Screen; Window while enabled) sends its own, through
`screenshot:capture` (page) or `screenshot:request-capture` (tray), and main remembers whichever mode
the capture ends in. Analytics: the handler of
`screenshot:capture` emits one `screenshot_captured` event per answered request with
`{ mode, platform, displays, outcome }` and nothing else. `outcome` is `captured`,
`cancelled`, `unsupported` or `failed`; `failed` is a provider throw, which the renderer still
receives as `cancelled`.

**Recording from the overlay (ADR 0030).** `screenshot:capture` with `intent: "record"` (the
`recordArea` shortcut) opens the overlay with `&intent=record` in its query: Enter answers
`select`, R answers `record`, and the Frame box starts from
`AppSettings.recordingArea` instead of `screenshotFrame`. In either intent a `record` or
`select` answer takes no pixels: the provider returns `{ kind: "record", start, displayId,
rect }`, the handler hands it to main's `onRecordTarget` and answers the renderer
`{ kind: "cancelled" }`, and nothing goes into `screenshot_captured`. Main then calls the hub's
`selectArea`, which writes `RecordingSettings.selectedSource` (that display's `screen:`
source) and `RecordingSettings.area` (or `null` for a whole display) and broadcasts
`recording-settings:changed`; `record` continues through the same path as the tray's Start.

## Canales fuera del mapa

Tres canales usan strings crudos en vez de `IPC_CHANNELS` (los dos lados los repiten a mano — si se renombra uno solo, falla en runtime sin error de compilación). Centralizarlos es un follow-up:

- `recording:get-screen-sources` — `getScreenSources()` (`recording-sources.ts`)
- `capture-panel:resize` — `resizeCapturePanel(height)` (`capture-panel-window.ts`)
- `capture-panel:open-main` — `openMainWindow()` (`index.ts`)

(El handler `ping` en `index.ts` es un leftover de test, sin uso.)

## `invoke` vs `send`

- **`invoke`** (request/response) — cualquier cosa que devuelve un valor o necesita confirmación (settings, library, permisos, `recording:create/finalize/abort`, `recording:get-state`).
- **`send`** (fire-and-forget) — el hot path y los eventos sin respuesta: `recording:write`, `recording:report-tick`, `recording:start/stop`, `control:command`, los broadcasts main→render (`settings:changed`, `recording:state`, `library:changed`, `control:tick`, `recording:command`, `screenshot:hotkey`), y los imperativos del panel.

## Tipos compartidos

Todos en `src/shared/types/`, puros (sin `electron`/`node:*`):

| Tipo                                                      | Archivo              | Qué describe                                 |
| --------------------------------------------------------- | -------------------- | -------------------------------------------- |
| `IPC_CHANNELS`, `IpcChannel`                              | `ipc.ts`             | Nombres de canal + tipo unión (autoritativo) |
| `AppSettings`, `Theme`, `DEFAULT_SETTINGS`                | `ipc.ts`             | Settings de la app                           |
| `RecordingActivity`, `RecordingSettings`, `RecordingTick` | `ipc.ts`             | Estado de grabación cross-window             |
| `KaipuElectronAPI`                                        | `electron-api.ts`    | La forma completa de `window.electronAPI`    |
| `ScreenSource`, `PermissionKind`, `PermissionStatus`      | `electron-api.ts`    | Captura y permisos                           |
| `LocalRecording`, `VaultDirectory`                        | `library-storage.ts` | Vault                                        |

## Gotchas

- ⚠️ El bridge solo expone métodos con un handler vivo en main (comentario en `preload/index.ts`). Agregar un método a `KaipuElectronAPI` sin registrar su handler compila pero falla en runtime.
- ⚠️ Los tres [canales fuera del mapa](#canales-fuera-del-mapa) están hardcodeados como strings en ambos lados. Si se centralizan en `IPC_CHANNELS`, cambiar los dos lados a la vez.
- ⚠️ Este doc agrupa para orientar, pero **la lista exacta vive en `IPC_CHANNELS`/`KaipuElectronAPI`** — al agregar un canal, agregalo ahí (lo verifica el compilador) y sumalo a la tabla del subsistema que corresponda.
