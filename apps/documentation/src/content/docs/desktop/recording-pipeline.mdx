## Captura

**Método:** `navigator.mediaDevices.getDisplayMedia()` en el renderer.

Tres estrategias en cascada:

1. Audio con constraints explícitas (`echoCancellation: false`, 48kHz, stereo)
2. `audio: true` simple
3. Solo video como último fallback

El main process usa `desktopCapturer.getSources()` para listar pantallas.

**Archivo:** `src/features/recording/hooks/useMediaRecorder.ts`

---

## Encoder

`MediaRecorder` con:

```
mimeType: 'video/webm;codecs=vp9,opus'
videoBitsPerSecond: 2_500_000  (configurable por settings)
chunk interval: 1000 ms
```

Webcam en paralelo:

```
mimeType: 'video/webm;codecs=vp9'
videoBitsPerSecond: 1_000_000
```

**Encode corre en el renderer** — compite con el thread de React.

---

## Data handling — streaming a disco

**No hay acumulación en memoria.** Anti-OOM para grabaciones largas.

```
ondataavailable → blob → base64 (renderer)
  → IPC recording:append-chunk → main
  → WriteStream (backpressure, 1 MB buffer)
  → archivo temp en app.getPath('temp')
  → al parar: finalize → move → vault del usuario
```

**Archivo:** `src/features/recording/hooks/useMediaRecorder.ts`, `src/main.ts`

---

## Post-procesamiento

**Screen-only:** WebM directo del MediaRecorder → `remuxWebmInPlace` agrega header de duración.

**Con webcam:** MP4 via re-encode FFmpeg post-grabación (`VideoComposer`, CRF 20, 4 threads, target 30fps).

**Thumbnail:** PNG 320×240 extraído al segundo 1, en background (no bloquea).

## Arquitectura implementada (kaipu-record)

El core real está construido sobre **mediabunny/WebCodecs**, no `MediaRecorder`+FFmpeg. Sigue el modelo **Opción A**: el renderer de la ventana principal (oculta mientras grabás) captura y encodea; el main escribe a disco; una ventana flotante aparte muestra la barra de control.

```
Ventana principal (oculta)                  Barra flotante (ventana aparte)
 useScreenRecorder                           ControlBar  timer · 5 barras · ⏸/▶ · ■
  getUserMedia(chromeMediaSourceId) ─┐
  getUserMedia(mic) + sys audio ─────┤─► MediaStreamVideo/AudioTrackSource
  AudioContext mix + AnalyserNode    └─► Output(Mp4OutputFormat, StreamTarget)
                                          → chunks { data, position } ─┐
        ┌──────────────────────── main process ───────────────────────┘
        │ recording-writer  fd.write(buf, 0, len, position)  (posicional, no append)
        │ recording-hub     relay estado↔comandos · oculta/muestra la principal
        │ finalize → vault <id>.mp4 + sidecar (título, duración, thumbnail)
        └──────────────────────────────────────────────────────────────
```

**Piezas:**

- `features/recording/recorder-store.ts` — **module-singleton** que posee el engine, la sesión del writer y el countdown (3-2-1 por defecto; Settings → Recording lo cambia a 5 s o lo apaga con 0, y se lee al pedir el inicio). Deliberadamente vive fuera de React (mismo patrón que `ui/toast-store.ts`): sobrevive a navegación, remounts de página y desvíos al editor de screenshots. Ver [El engine ya no vive en la página](#el-engine-ya-no-vive-en-la-página) abajo.
- `features/recording/hooks/use-screen-recorder.ts` — binding fino de React sobre el store vía `useSyncExternalStore`; ya no tiene lógica propia.
- `features/recording/recorder-engine.ts` — captura + mezcla de audio + encode mediabunny (MP4 H.264/AAC). Seam `videoProvider`/`audioProvider` para meter cámara/watermark después sin tocar lo de abajo.
- `features/recording/elapsed.ts` + `audio-levels.ts` — lógica pura testeada (clock con pausa, RMS→5 barras).
- `features/control-bar/` — barra flotante con nuestros tokens/`cx()`/`data-*`.
- `main/recording/recording-writer.ts` — escritura **posicional** + finalize al vault. Drena los writes en vuelo antes de cerrar el handle (los chunks llegan fire-and-forget por IPC).
- `main/recording/control-bar-window.ts` — `BrowserWindow` frameless/transparent/always-on-top, abajo-centro de la pantalla.
- `main/recording/recording-hub.ts` — relay de estado/comandos + oculta/muestra la ventana principal.

**IPC nuevo:** `recording:create|write|finalize|abort` (writer) · `recording:report-tick` → `control:tick` (estado → barra) · `control:command` → `recording:command` (botones → grabador) · `recording:start|stop` (mostrar/ocultar ventanas) · `recording:hide-main-window` (invoke at the end of the countdown: hides the main window and answers whether it was on screen).

**Vault:** ahora es agnóstico de extensión (`.mp4`/`.webm`), con sidecar de duración + thumbnail; `kaipu-media://thumb/<id>` sirve el póster.

### El engine ya no vive en la página

**Problema (encontrado en la auditoría pre-testers, findings 1/2/5/9/10/20/23/24/25):**
el engine, la sesión del writer y el countdown vivían en refs de React dentro de
`useScreenRecorder`, instanciado por el Record page. Cualquier unmount de esa
página — navegar, tomar un screenshot a mitad de grabación, el rescate
`⌘⌃O` reabriendo la ventana y remontando el Record page — dejaba el engine
huérfano: seguía grabando (o el listener de comandos moría con el unmount),
pero Stop/Pause dejaban de tener efecto porque apuntaban a una instancia de
hook que ya no existía.

**Solución:** el engine + countdown ahora viven en `recorder-store.ts`, un
**module-singleton** (mismo patrón que `ui/toast-store.ts`): funciones planas
mutan estado de módulo y notifican suscriptores vía `useSyncExternalStore`. El
listener `onRecordingCommand` (pause/resume/stop desde la barra o el atajo
global) se registra **una sola vez, a nivel de módulo** — no dentro de un
efecto de React atado al mount de una página — así que sobrevive a cualquier
navegación. Con esto:

- Remontar el Record page (p. ej. tras `⌘⌃O`) ya no resetea nada: todas las
  instancias de `useScreenRecorder` en la misma ventana leen el mismo estado.
- El **stop de la barra/atajo global cancela un countdown en curso** en vez de
  ser ignorado — antes solo actuaba sobre un engine ya vivo.
- La navegación al terminar (`/library/:id`) se dispara desde una suscripción
  en `AppShell` (el layout que nunca se desmonta entre rutas), no desde un
  callback pasado a `useRecordingSetup` por la página activa.
- El screenshot (hotkey, botón del tray, o desde la página de Screenshots) se
  **bloquea con un toast** si el store no está `idle` — cubre tanto una
  grabación activa como el propio countdown/`starting`, donde antes el
  selector nativo de región corría contra el arranque del engine.
- The main window is hidden (`recording:hide-main-window` + `recordingStart`)
  **before the take encodes its first frame**, not after — the app itself used to
  show in the first ~0.5-1 s of every recording. See
  [Start sequence](#start-sequence-acquiring-during-the-countdown).
- `fastStart: false` (antes `"in-memory"`) — mediabunny escribe a disco
  progresivamente en vez de bufferear la grabación completa en RAM del
  renderer hasta el stop (eso hacía OOM-crashear grabaciones largas y perder
  todo si la app moría antes del stop).

### Estado global de grabación (entre ventanas)

**Problema:** cada ventana (Record page, Capture Panel) tiene su propia instancia
de `useScreenRecorder` — comparten _código, no estado_. Sin coordinación, el
Capture Panel (otra ventana) no sabe que hay una grabación activa y mostraría
"Start Recording", permitiendo arrancar una segunda grabación → errores.

**Solución:** el `recording-hub` (main, única fuente de verdad) mantiene
`RecordingActivity { active, status }` y lo **transmite a todas las ventanas**
(`recording:state`) en cada transición (start/stop/pause/resume), re-emitiendo
solo cuando el status cambia — no en cada tick de 10/s. Cada ventana lee esto con
**`useRecordingActivity()`**, que además **consulta `getRecordingState()` al
montar** (por si una ventana se abre con la grabación ya en curso). Con eso:

- **Record page:** una **tarjeta de cabecera** con "Recording"/"Paused" + **timer
  en vivo**, la fuente con badge **LOCKED**, y una fila **Pause / Stop recording**
  (pause/resume expuestos desde `useRecordingSetup`); los controles de setup quedan
  `inert`.
- **Capture Panel:** un **banner rojo "Recording — mm:ss"** con timer en vivo,
  controles `inert`, y el botón pasa a **"Stop Recording"** (comando stop al hub) —
  imposible arrancar una segunda grabación desde el tray.

El timer en vivo de ambas ventanas sale de `RecordingActivity.elapsedSeconds`, que
el hub actualiza desde los ticks del grabador y re-emite ~1/s (no en cada tick de
10/s).

**Settings compartidos (misma idea, bidireccional).** La fuente, los toggles
(mic/audio/cámara) y el micrófono seleccionado viven en el hub como `RecordingSettings`
— **una sola fuente de verdad** para todas las ventanas. `useRecordingSettings` (en el
renderer) consulta al montar, se suscribe a cambios y **escribe optimista** vía
`recording-settings:update`; el hub mergea, **re-emite a todas las ventanas** y de paso
maneja la burbuja de cámara. `useRecordingSetup` toma esos campos del estado global y deja
local solo la UI transitoria (picker/menú abiertos, countdown) y el ciclo de grabación.
Resultado: cambiás un toggle en la app o en el panel y **se refleja en ambos**.

### Cámara bubble (ventana flotante capturada)

La cámara es una **burbuja flotante** (`?window=camera-bubble`): una `BrowserWindow`
circular, frameless/transparent/always-on-top, arrastrable, que muestra el webcam vía el
hook testeado `useCameraPreview`. **No se compone en canvas** — como está en pantalla, la
captura de pantalla la incluye en el video. La maneja el toggle Cámara del Record page
(`camera:set` → `recording-hub` → `CameraBubbleWindow.show/hide`).

Para que **la barra de control NO salga en el video** pero **la cámara sí**, la ventana de
la barra usa `setContentProtection(true)` (macOS: `NSWindowSharingNone`); la burbuja
deliberadamente no la usa. _(Verificar en runtime que el screen-capture respeta la exclusión.)_

La burbuja se maneja desde el **estado global de settings** (ver abajo): el hub la
muestra/oculta según el toggle global de Cámara, así que **funciona prendiéndola desde la
app o desde el Capture Panel**. Follow-ups: selector de dispositivo de cámara, resize/forma.

**Se esconde durante un screenshot.** Como es always-on-top y no tiene content-protection
(a propósito — para que la grabación la capture), quedaba dentro del selector nativo de
región en cualquier captura de pantalla mientras la cámara estaba prendida. `beforeCapture`/
`afterCapture` (`main/index.ts`) llaman a `hub.hideCameraBubbleForCapture()` /
`restoreCameraBubbleAfterCapture()`, que usan `hide()`/`show()` (no `destroy()`) — la
cámara sigue tomada por `getUserMedia` todo el tiempo, así que no hay parpadeo del punto
verde de "en uso".

### Calidad configurable (presets + sliders)

La calidad de grabación es un **modelo puro** en `src/shared/recording-quality.ts` (sin
imports de electron/node/react), compartido por main (validación) y renderer (UI + wiring):

- **Tres knobs** (`RecordingQuality { resolution, fps, bitrate }`) con pasos discretos.
  `resolution` 720/1080/1440/2160 → dimensiones 16:9; `fps` 24/30/48/60; `bitrate`
  light/medium/high/max → 4/8/16/24 Mbps. El **peso ≈ bitrate** (`mbPerMinute`).
- **Presets como vista derivada:** `activePreset(quality)` matchea contra Liviano (720/24/
  light), Equilibrado (1080/30/medium) y Máxima calidad (1440/60/high); si no matchea →
  `"custom"`. No se guarda `preset` aparte, así que **no hay desync** preset/valores: clickear
  un chip aplica el combo; mover cualquier slider cae en Personalizado. 4K y bitrate máximo
  solo se alcanzan en Personalizado.
- **Persistencia:** vive en `AppSettings.recordingQuality` (reusa el `settings-store` +
  `settings:get/update`), validado por `sanitizeQuality` en `mergeSettings`.
- **Wiring al encoder:** `qualityToEngine(quality)` → `{ width, height, frameRate,
videoBitrate }`. `use-recording-setup` lo lee en mount (ref) y lo pasa por `StartInput` →
  `useScreenRecorder` → `prepareEngine`. El engine usa esos valores en las constraints
  `maxWidth/maxHeight/maxFrameRate` y en el bitrate del track. **El `maxWidth/Height` es un
  techo: no upscalea** sobre la resolución nativa de la pantalla.
- **Una sola fuente para los números de encode:** el engine **no reescribe** ningún valor —
  su fallback es `qualityToEngine(DEFAULT_QUALITY)` (preserva 1080p30·8 Mbps para
  callers/tests que omiten los campos), y el bitrate de audio sale de `AUDIO_BITRATE_BPS`.
  Todo (resoluciones, bitrates, presets, default, audio) vive en `recording-quality.ts`.
- **Sin enums:** los sets (`RESOLUTION_STEPS`, `FPS_STEPS`, `BITRATE_STEPS`, `NAMED_PRESETS`,
  `PRESET_ORDER`) son arrays `as const` y el tipo se deriva con `(typeof X)[number]` — ver
  [Enums: as const, not enum](/architecture/enums-as-const).
- **UI** (`pages/settings/recording-quality-settings.tsx`): chips con emoji + caption que
  cambia por preset + tres sliders discretos con label semántico (Cine/Estándar/Muy fluido,
  ≈MB/min) y un **ⓘ** (popover) por slider. Copy en español neutro, orientado al beneficio.

### Watermark (free → paid)

Un watermark (wordmark "Kaipu") **quemado en el video** solo para usuarios free; pagar lo
quita. La decisión está **centralizada en un solo hook** — el resto de la app (engine
incluido) no sabe de planes ni flags.

- **`useWatermark()`** (`features/watermark/use-watermark.ts`) es el único seam. Compone tres
  inputs, hoy stubs: `entitlement.isPaid` (TODO backend), `featureFlag` (TODO PostHog) y un
  **override de dev**. La regla pura `resolveWatermarkEnabled({flagOn, isPaid, devForce})` =
  `flagOn && !paid`. Devuelve `{ enabled, config }`.
- **Toggle de dev que NUNCA llega a prod:** un switch en Settings ("Quitar watermark — simular
  plan pago"), **visible solo en dev**, guarda el override en `localStorage`
  (`features/watermark/dev-override.ts`). Tanto la sección del toggle como la lectura están
  gateadas por `import.meta.env.DEV` (literal en build), así que se **eliminan del bundle de
  producción** — y un usuario no puede sacarse el watermark seteando localStorage a mano. Como
  se lee en cada render y cambiar de Settings→Record remonta el consumidor, el flip aplica
  **sin reiniciar**.
- **Draw-pass (canvas compositor)** `watermark-compositor.ts`: el screen track va a un
  `<canvas>` (frame + el asset re-teñido a **silueta blanca** con sombra suave, en la esquina
  vía `watermarkRect`), y se re-captura con `canvas.captureStream(frameRate)`. Ese track va al
  encoder. **Costo cero cuando está apagado:** si `enabled === false` se encodea el screen
  track directo (sin canvas). La detección de fallas sigue mirando el `screenTrack` original.
- **Wiring:** `useWatermark()` → `use-recording-setup` (ref) → `StartInput.watermark` →
  `prepareEngine`. `EngineOptions.watermark` decide compositar o no; `stop()` corta el draw loop.
- **Config** (`watermark.ts`, sets `as const`): variant (wordmark/mark), position, tint
  (white/original), opacity, height/margin ratios. Default: wordmark · centro-derecha · white.

**Pendiente (#6 real):** el `isPaid`/flag son stubs — el gating real depende de #4 (PostHog +
entitlement). El seam ya está, así que enchufarlo no toca nada más.

### Recuperación de fallas (no quedar trabado)

Las rutas de error restauran **siempre** el estado de la app:

- **Start failure** (permission denied, `getUserMedia` fails, the screen capture ends):
  the window is hidden optimistically when the countdown ends, before the take is set up
  (see [Start sequence](#start-sequence-acquiring-during-the-countdown)), so `beginTake`'s
  `catch` undoes that hide explicitly — it calls `recordingStop()` (show window + restore
  Dock + hide bar), releases the engine and aborts the session — and goes back to `idle`
  (no separate `error` state), so Start is usable at once. A failure during the countdown
  is held (`PendingStart.failure`, or the rejected acquisition) and fails the start when
  the countdown ends, the same way.
- **Falla al finalizar:** `recordingStop()` se llama **siempre**, fuera del try/catch.
- **Falla a mitad de grabación** (encoder error, o el track de pantalla termina porque el
  usuario corta el screen-share): el engine la expone vía `onError` (el `errorPromise` de
  las sources + el evento `ended` del track de pantalla) → corre el mismo `stop()` robusto
  (finaliza-o-aborta + restaura todo). Un flag `stopping` en el store evita doble-teardown
  si el usuario toca Stop y la falla disparan a la vez.
- **El renderer principal muere o la ventana se cierra a mitad de grabación** (crash, OOM,
  o Cmd+W/botón rojo): no llega `recordingStop` desde un renderer muerto, así que
  `recording-hub.ts` expone `forceReset()` (reseteo best-effort de `activity` + Dock +
  barra) llamado desde `render-process-gone` en main. Cerrar la ventana mientras
  `activity.active` además dispara un diálogo de confirmación ("Detener y cerrar") que
  corre el stop normal (con timeout de 5s) antes de dejar cerrar — así el archivo se
  finaliza con lo grabado hasta ese momento en vez de perderse. Así la app **nunca queda
  trabada** con la ventana oculta, la barra colgada, o el Capture Panel bloqueado.
- **Cmd+Q / Quit del tray a mitad de grabación** (`before-quit`): mismo patrón que el
  cierre de ventana — si `hub.isActive()`, `preventDefault` + confirmación ("Detener y
  salir"), se manda el comando `stop`, y recién cuando llega `recordingStop` (o pasa el
  timeout de 5s) se hace `app.quit()`. Con el fastStart en disco (ya no en memoria) el
  archivo queda finalizado con lo grabado hasta ese momento, en vez de descartarse entero.

### Gotcha: ocultar la ventana principal y el Dock/Cmd+Tab (macOS)

El hub **oculta la ventana principal mientras grabás** (`mainWindow.hide()`) para que
solo se vea la barra flotante. En macOS, ocultar la única ventana puede **sacar la app
del Dock y del switcher (Cmd+Tab)**, y `show()` no siempre la devuelve. Por eso, al
**detener**, el hub **re-afirma la activation policy** (`applyDockPolicy()`) y trae la app
al frente (`app.focus({ steal: true })`) — así vuelve al Cmd+Tab.

La visibilidad en el Dock/switcher es ahora un **setting persistido** (`showInDock`):
`regular` (con Dock + Cmd+Tab) vs `accessory` (solo barra de menú/tray). Vive en
`infrastructure/settings-store.ts` (la primera infra de settings persistidos de la app) y
se togglea desde Settings.

### Start sequence: acquiring during the countdown

A take's acquisition — session file (`recording:create`), screen `getUserMedia`, frame-size
measurement, compositor, mic, audio mix, encoder, cursor track — costs about a second. It
used to start when the countdown reached 0, so every take spent that second in
"Starting…". It now runs **during** the countdown, and the take starts within tens of
milliseconds of the countdown's end.

1. **Countdown on screen** (`countdownVisible`): the clock of the numbers starts, and
   `acquireDuringCountdown` resolves the input and calls `acquireStart`: it creates the
   session file, then `prepareEngine` and `beginCursorTrackSession` concurrently. Nothing
   is encoded and the app is not hidden. The mark `acquired during countdown` says it
   finished before 0.
2. **Countdown ends** (`startTake`): the input is resolved again — that one is the take's.
   If anything that decides the acquisition changed (`acquisitionKey`: source, area, mic,
   system audio, quality, watermark), the early acquisition is released and the take
   acquires again, as it did before. The status goes to `"starting"`.
3. **Hide the app**: `recording:hide-main-window` (invoke) is sent, then `recordingStart`
   (bar, shade, Esc released). Main answers the invoke before handling `recordingStart`
   (same IPC pipe, in order) with whether the window was on screen. On the Record page's
   countdown it was: the take waits `WINDOW_HIDE_SETTLE_MS` (50 ms) so the frames in flight
   when the window is ordered out are not its first. For a region countdown the window was
   already hidden and nothing is waited.
4. **Begin** (`beginTake`): once acquired and hidden, `PreparedEngine.begin()` calls
   `output.start()` (a few ms), the clock starts and the first tick goes to the bar at once,
   so it leaves "Starting…" immediately. Marks: `clock started at countdown end +Nms`, then
   `status recording`.

**How the countdown stays out of the file.** `prepareEngine` builds the `Output` and its
`MediaStreamVideo/AudioTrackSource`s but does not start the output; no frame is read from
the tracks until `begin()`. The sources are not started-and-paused instead, because
mediabunny cannot pause a source before its first frame: the frame-rate sampler's `tick`
asserts on a time base that only the first unpaused frame sets, and the take fails when it
resumes. With `timestampBase: "synced-zero"`, the first frame after `begin()` sets
`_firstMediaStreamTimestamp`, so the take's duration (`startElapsed` right after `begin`),
its video time 0 and the cursor track's anchor (`firstMediaTimestamp`) all start at the end
of the countdown. The poster thumbnail is also taken in `begin()`: during a Record-page
countdown the screen still shows the app. Pointer samples and clicks taken during the
countdown are before the anchor and are dropped by `buildCursorTrack`.

**Cancel and failure.** A cancel during the countdown (Esc, Stop, the cancel button) calls
`discardStart`: `PreparedEngine.release()` stops the screen and mic tracks, the compositor
and the audio context, and `recording:abort` deletes the session file and discards main's
cursor track. An acquisition still in flight is released when it settles. `release()` after
`begin()` stops the take instead, so a cancel at any moment leaves no device open. An engine
`onError` during the countdown (the screen capture ends) is held in `PendingStart.failure`
and fails the start the usual way when the countdown ends. macOS shows its recording
indicator from acquisition on, so during the countdown too.

With the countdown off nothing changes: the take acquires at once, after the hide is asked
for, and starts when acquired.

### El hueco "starting" después del countdown

After the countdown (`3·2·1` by default, `5·4·3·2·1` or none per Settings), the recorder is
in **`"starting"`** until the take encodes: tens of milliseconds when the countdown covered
the acquisition (above), as long as the acquisition still needs otherwise. There
`isRecording` is still `false`, so the Start button used to be visible and clickable for
~0.5–1 s (a second recording could be triggered). It is closed from three sides:

- El **overlay del countdown sigue arriba durante `"starting"`** mostrando un
  spinner (su `value` pasa de número a `null`). Como el overlay es un backdrop que
  captura clicks, el botón no se puede tocar en ese intervalo. No hay parpadeo:
  `clearCountdown()` y `setStatus("starting")` ocurren en el mismo tick, así que la
  condición `countdown !== null || isStarting` nunca queda en falso.
- **Guard de re-entrada** en `useScreenRecorder.start`: chequea
  `engineRef || sessionRef`, y `sessionRef` se setea sincrónicamente, así que un
  segundo `start()` durante "starting" retorna de inmediato — sin doble sesión.
- El botón Start queda `disabled` durante el countdown y "starting" (defensa extra).

`useRecordingSetup` expone `recordingStatus` (el `RecorderStatus` completo) para que
el Record page distinga "starting". El número del countdown usa el color de acento.

**Cancelable at any moment.** `CountdownOverlay` has a visible "Cancel" button and an
Escape handler, both wired to `stopOrCancelRecording()` — the same function the bar and the
global stop shortcut use. One code path for the three phases: during `"counting"` it clears
the interval and releases whatever the countdown acquired; during `"starting"` it restores
the app at once and releases the start whenever its acquisition settles, instead of letting
the recording start anyway; with a live engine, it finalizes normally.

### Después de grabar: navegación + estado "Saving"

Al detener, `useScreenRecorder` muestra un breve estado **"Saving…"** en la barra
mientras el encoder hace flush y el archivo se finaliza (metadata, thumbnail,
nombre) — `recordingFinalize` solo resuelve cuando todo eso existe en el vault, así
que la espera es real, no artificial (con un mínimo de ~600ms para que no parpadee
en clips cortos). Luego dispara `onComplete(recording)` que navega a
`/library/:id` **antes** de volver a mostrar la ventana principal, para aterrizar
directo en el detalle del video (sin flash del Record page). El detalle tiene su
propio "Loading…" mientras `useLocalLibrary` re-lista el vault.

The bar window is hidden on stop, not destroyed, so it would otherwise keep that
"Saving…" into the next take. Its other state is **"Starting…"** (muted dot, Stop
only, no timer): `ControlBarWindow.hide()` and the hub's `recordingStart` reset it
to `CONTROL_BAR_STARTING_TICK`, and a new bar window opens on it. It lasts until the
recorder's first tick, sent the moment the take encodes — right at the end of the countdown
when the countdown acquired the take. Stop there cancels the
pending start. A bar hidden before its first window painted stays hidden.

### Ventanas flotantes transparentes (barra y burbuja)

La barra y la burbuja son `BrowserWindow` frameless/transparent/always-on-top.
Detalles que costaron y conviene recordar:

> **Dos causas de "caja oscura" sobre una ventana transparente** (ambas se ven
> parecidas, pero la raíz es distinta — confundirlas hace perder tiempo):
>
> 1. **Falta `backgroundColor: "#00000000"`** (junto con `transparent: true`): la
>    ventana pinta un fondo opaco que se ve como una caja oscura sobre fondos claros.
>    Obligatorio en **toda** ventana transparente.
> 2. **Un `box-shadow` de CSS más grande que el margen transparente de la ventana**:
>    la sombra **se recorta contra los bordes (rectangulares) de la ventana** y queda
>    una caja oscura. Regla: la sombra debe **desvanecerse por completo dentro del
>    margen** (window − elemento). Ej. burbuja: window 224 − círculo 192 = 16px de
>    margen, así que un blur de ~8px entra holgado; un blur de 18px se cortaba.

- **No debe scrollear.** El renderer marca `body[data-window="control-bar"]` y
  `main.css` la fija al viewport con `overflow: hidden` y le da a `#root` un
  _block-formatting context_, evitando que el margen superior del pill colapse
  hacia el body y empuje el documento más allá de los 64px (lo que sacaba una
  scrollbar — la global temada).
- **Diseño:** rectángulo redondeado (no pill), botones cuadrados redondeados,
  orden `punto · timer · separador · medidor de mic · pausa · stop · atajo`, sin
  focus-ring (el accent del SO lo hacía ver "preseleccionado"), sombra discreta.

### Encode por hardware (VideoToolbox) y el caveat de OpenH264

mediabunny pasa `hardwareAcceleration: 'no-preference'` por defecto, y en la build de
Chromium de Electron eso seleccionaba el **encoder H.264 por software (OpenH264)** —
visible como warnings `[OpenH264] ... bitrate can't be controlled...` en consola, e
implica más CPU/calor que el hardware. El engine ahora pide
**`hardwareAcceleration: "prefer-hardware"`** (+ `latencyMode: "realtime"` para
captura en vivo) en el `VideoEncodingConfig` del `MediaStreamVideoTrackSource`, para
empujar a **VideoToolbox**. Es un _hint_: si el encode H.264 por hardware no está
disponible vía WebCodecs, cae a software (el comportamiento previo, sin romper).

**Verificación:** el `onEncoderConfig` loguea el config real; si el hardware engancha,
los mensajes `[OpenH264]` **desaparecen** de la consola. (Los warnings
`representedObject is not a WeakPtrToElectronMenuModelAsNSObject` y
`sysctlbyname ... kern.hv_vmm_present failed` son ruido inofensivo de Electron/macOS.)

### Por qué mediabunny y no FFmpeg

No portamos el stack `MediaRecorder`+FFmpeg del legacy. Gran parte del rol de FFmpeg ahí era **parchear lo que `MediaRecorder` rompe** (WebM sin duration header → remux). mediabunny no usa `MediaRecorder`, así que esos parches no nacen.

| Aspecto          | Legacy                     | Implementado (mediabunny)                   |
| ---------------- | -------------------------- | ------------------------------------------- |
| Encoder          | `MediaRecorder` VP9/Opus   | WebCodecs H.264/AAC (HW, ~8× más rápido)    |
| Output           | WebM roto → remux FFmpeg   | MP4 seekable de un solo paso                |
| Hot path a disco | base64 → IPC → WriteStream | bytes crudos posicionados (`StreamTarget`)  |
| Compositing      | FFmpeg `filter_complex`    | canvas + `CanvasSource` en vivo (follow-up) |
| Bundle           | ~50–80MB binarios por arch | mediabunny tree-shakable, sin deps          |

Detalle y alternativas descartadas: [ADR 0001 — Mediabunny over FFmpeg](../architecture/decisions/0001-mediabunny-over-ffmpeg).

## Area recording (ADR 0030)

A recording can cover part of one display. The source is still that display's whole
`screen:` capture; the area travels in `RecordingSettings.area` and `RecordingStartInfo.area`
(display id, display-relative DIP rectangle, display size).

- **Who sets it.** Only main, in `selectArea`, together with that display's `screen:` source.
  A window's settings patch can clear the area but not set one, and a patch that changes the
  source clears it, so the area always names the display the source records. A display
  unplugged or resized after the choice drops the area and its source (after the take, if
  one is running); the next take asks again instead of cropping with the old size.

- **Crop.** After `getUserMedia`, the engine measures the track and `areaEncodePlan` maps the
  area to physical pixels of that track (`cropForSize`, the same DPI arithmetic the Windows
  screenshot backend uses), then caps its height with `fitToCap`. With an area the compositor
  always runs and draws only that source rectangle; display and window recordings call it
  exactly as before.
- **Shade.** While an area records, main shows `recording-shade-window.ts` on its display:
  clear inside the area with a 1.5 px accent outline, dimmed at 60 % outside, click-through,
  content-protected and one level below the control bar and the camera bubble.
- **Camera bubble.** Anchored to the area's bottom-left corner; hidden while the area cannot
  hold it (224 px plus 40 px margins), back in its corner at stop.
- **Cursor sidecar.** Normalized to the area, so `track.display` is the area's size and the
  editor's zoom needs no offset; an optional `region` keeps the area's origin.
- **Entry points.** The capture overlay's Record button in either intent and the `recordArea`
  shortcut. The widget and Record page redesign that adds a mode row waits for its design file.
