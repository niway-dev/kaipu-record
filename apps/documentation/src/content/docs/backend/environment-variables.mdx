# Environment Variables

**Where values live:** [Secrets layout — folders and tags](/deployment/secrets-layout/).
That document is the inventory — every variable, its Infisical folder, and which
apps read it.

**This document is about how they arrive.** The three runtimes in this repo read
their environment in incompatible ways, and that difference decides how each
script is written.

## One rule first

There are no hand-maintained `.env` files. Values come from Infisical, fetched at
start-up. Where a `.env` exists it is **generated and gitignored** — editing it
does nothing, because the next start overwrites it.

## Three delivery mechanisms

| Consumer                                    | Reads from                          | Delivered by                             |
| ------------------------------------------- | ----------------------------------- | ---------------------------------------- |
| Repo-root scripts, `vite dev`, test runners | `process.env`                       | `scripts/with-env.sh`                    |
| Cloudflare Workers (`wrangler`)             | Worker bindings                     | `scripts/pull-env.sh` → generated `.env` |
| Electron / Vite builds                      | `import.meta.env`, inlined at build | `scripts/with-env.sh` around the build   |

### Process injection — most things

```bash
bash scripts/with-env.sh --tags db-scripts -- turbo run db:push
```

`infisical run` puts the values in the child process's environment. Anything
reading `process.env` sees them.

The wrapper requires an explicit `--tags` or `--path` filter. There is no
"fetch everything" mode: a desktop build has no business holding a database
credential.

### A generated file — Cloudflare Workers only

A Worker reads **bindings**, not the parent process environment. Injecting into
`wrangler`'s process never reaches the Worker, so the values must arrive in a
file that wrangler loads:

```json
"env:pull": "bash ../../scripts/pull-env.sh server-hono .env",
"dev": "bun run env:pull && wrangler dev"
```

`pull-env.sh` iterates folders because **`infisical export` has no `--recursive`
flag**, while `infisical run` does. It writes the file `0600` and fails loudly
when a tag matches nothing.

### Build-time inlining — the desktop app

`apps/kaipu-record` has no env module. electron-vite inlines `MAIN_VITE_*` (main
process) and `VITE_*` (renderer) at build time, and needs no special integration
because Vite's `loadEnv` reads `process.env` **after** the `.env` files and lets
it win:

```js
for (const [key, value] of Object.entries(parsed))   // .env files first
  if (prefixes.some(p => key.startsWith(p))) env[key] = value;
for (const key in process.env)                        // process.env second — wins
  if (prefixes.some(p => key.startsWith(p))) env[key] = process.env[key];
```

The discipline this imposes: names in Infisical must carry the **exact prefix**
the bundler expects. A mismatched prefix is ignored silently — verify by
grepping the built bundle for an expected value, not by a green exit code.

## Two behaviours that will surprise you

**Infisical overrides variables already set in your shell.** dotenvx, which this
replaced, did the opposite. `DATABASE_URL=<other> bun run plan` therefore runs
against the Infisical value, not yours. Use `SKIP_INFISICAL=1` to supply values
yourself — see [Commands](/commands/).

**An untagged secret is silently absent.** A tag filter that matches nothing
yields an empty environment rather than an error. `pull-env.sh` guards against
this; `with-env.sh` does not yet. Tag a secret as you create it.

## Builds must not depend on the CLI

`with-env.sh` passes straight through when `CI` is set. CI supplies its own
values through the workflow and builds with placeholders on purpose — requiring
a secrets CLI there would couple the build to something it does not need.

This is why `bun run build` for the desktop app is **not** wrapped: a build
consumes whatever environment it is given. Wrapping it once caused a signed
local build to bake development endpoints into a distributable.

## Validation

`@kaipu/infra-env` holds the zod schemas (`serverEnvSchema`, `webServerEnvSchema`,
`webClientEnvSchema`) that parse and type the values once they arrive. It is the
committed declaration of what each app requires, and a missing required variable
fails there — loudly, at boot.

`apps/console` deliberately does not use it: it reads bindings directly with
fallbacks.
