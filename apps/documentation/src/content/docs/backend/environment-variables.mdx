# Environment Variables

All environment values come from [Infisical](https://infisical.com). There are no
hand-maintained `.env` files — where one exists on disk, it is **generated** by a script,
gitignored, and never edited by hand. Changing a value means changing it in Infisical and
restarting the affected command; editing a generated file locally only lasts until the next
generation.

An earlier proposal evaluated managing encrypted `.env` files with
[dotenvx](https://dotenvx.com) instead. It was rejected in favour of Infisical; see
[Rejected: dotenvx for encrypted env management](/specs/2026-06-15-dotenvx-env-management-proposal/)
for that record and why.

:::note[This is today's state, not the final one]
A further migration to [varlock](https://varlock.dev) on top of Infisical is designed and
in flight — typed schemas, `varlock-wrangler` for Worker deploys, and the removal of the
remaining per-app `.env` generation. It is a six-phase plan and **no phase has merged yet**.
The spec lands with PR #112 (design) and phase 1 with PR #113. Read them before changing
anything on this page, so a fix does not collide with a phase that already owns it — and see
[Secrets and dependency audit — handoff](/backlog/secrets-and-dependency-audit-handoff/) for
the current state of that work.
:::

## Layout in Infisical

- Environment slug: `dev` (the Infisical UI shows it as "Development").
- Secrets live in six folders, grouped by blast radius rather than by which app reads them:
  `/public`, `/database`, `/cloudflare`, `/auth`, `/email`, `/signing`. Tags name the consumer.
- Non-secret config lives at the Infisical root.

## How commands get their environment

Infisical is only contacted by one command, `bun env:pull` (`scripts/env-pull.sh`). It
generates a gitignored `.env` per consumer, filtered by tag, and everything else reads those
files — so an Infisical outage blocks a refresh, never a dev session.

| File                     | Tag            | Read by                                                        |
| ------------------------ | -------------- | -------------------------------------------------------------- |
| `apps/server-hono/.env`  | `server-hono`  | `wrangler dev`                                                 |
| `apps/web-hono/.env`     | `web-hono`     | `vite dev`, `wrangler dev`                                     |
| `apps/console/.env`      | `console`      | `vite dev`                                                     |
| `apps/kaipu-record/.env` | `kaipu-record` | `electron-vite dev`, `test:e2e`                                |
| `packages/infra-db/.env` | `db-scripts`   | root `db:*`, `plan`, `test:integration` (via `bun --env-file`) |

- **All or nothing.** Every file is fetched to a temp directory first; the real files are
  replaced only when every fetch succeeded. A failure leaves every existing `.env` as it was.
- **Owner-only.** Files are written with mode `600`. The script prints counts, never values.
- **Fail fast.** `scripts/require-env.sh` stops `dev` and the database scripts when their file
  is missing, and the Zod schemas validate through `parseEnv` from `@kaipu/infra-env`. Both
  point to `bun env:pull`. `require-env.sh` passes straight through when `CI` is set: workflows
  inject their own values and never need a secrets CLI.
- **Inline overrides win.** For the database scripts a variable set in the shell beats the file:
  `DATABASE_URL='<production url>' bun run plan grant <email>`.

`scripts/with-env.sh` (live `infisical run`) remains only for the signed production build in
`apps/kaipu-record/scripts/build-mac-local.sh`.

## First-time setup

Once per machine:

```bash
bun run setup      # reports which global tools are missing, and how to install them
infisical login
bun env:pull       # from the repo root
```

`scripts/setup-dev.sh` only checks — it never installs. Run `bun env:pull` again whenever a
value changes in Infisical, a variable is added, or an app reports a missing variable.

## Rules

- Never hand-write or hand-edit a generated `.env` file; the next pull overwrites it.
- Adding a new Infisical folder means adding it to the `FOLDERS` list in
  `scripts/env-pull.sh` too, or its secrets go missing from generated files without any error.
  A new consumer means a new entry in `TARGETS`.
- Never print secret values in logs, commits, or documentation.
