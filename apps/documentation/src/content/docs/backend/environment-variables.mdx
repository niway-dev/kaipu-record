# Environment Variables

All environment values come from [Infisical](https://infisical.com). There are no
hand-maintained `.env` files — where one exists on disk, it is **generated** by a script,
gitignored, and never edited by hand. Changing a value means changing it in Infisical and
restarting the affected command; editing a generated file locally only lasts until the next
generation.

An earlier proposal evaluated managing encrypted `.env` files with
[dotenvx](https://dotenvx.com) instead. It was rejected in favour of Infisical; see
[Rejected: dotenvx for encrypted env management](/specs/2026-06-15-dotenvx-env-management-proposal/)
for that record and why.

:::note[This is today's state, not the final one]
A further migration to [varlock](https://varlock.dev) on top of Infisical is designed and
in flight — typed schemas, `varlock-wrangler` for Worker deploys, and the removal of the
remaining per-app `.env` generation. It is a six-phase plan and **no phase has merged yet**.
The spec lands with PR #112 (design) and phase 1 with PR #113. Read them before changing
anything on this page, so a fix does not collide with a phase that already owns it — and see
[Secrets and dependency audit — handoff](/backlog/secrets-and-dependency-audit-handoff/) for
the current state of that work.
:::

## Layout in Infisical

- Environment slug: `dev` (the Infisical UI shows it as "Development").
- Secrets live in four folders, grouped by blast radius rather than by which app reads them:
  `/cloudflare`, `/database`, `/server-hono`, `/kaipu-record`.
- Non-secret config lives at the Infisical root.

## How commands get their environment

Two different mechanisms exist because Cloudflare Workers need env differently from everything
else:

| Mechanism                                | Used by                                                           | How                                                                                                                                                                                                                                             |
| ---------------------------------------- | ----------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `scripts/with-env.sh`                    | Most commands — `bun run dev`, `db:*`, `test:integration`, `plan` | Wraps the command with `infisical run`, injecting values into the process environment. Requires an explicit `--tags` or `--path` filter — there is no "fetch everything" mode.                                                                  |
| `scripts/pull-env.sh` (generated `.env`) | Cloudflare Workers (`apps/server-hono`, `apps/web-hono`)          | `wrangler` reads Worker bindings from a file, not from the parent process, so `infisical run` never reaches the Worker. This script writes a gitignored `.env` file with exactly one consumer's secrets, filtered by tag, for wrangler to read. |

Both scripts pass straight through when `CI` is set (CI builds with placeholder values on
purpose and must not need a secrets CLI) and both fail loudly if the Infisical CLI is missing
locally, rather than silently building with undefined values.

`scripts/with-env.sh` also honours `SKIP_INFISICAL=1` as an escape hatch for an operator who
wants to supply values directly — for example
`DATABASE_URL='<production url>' SKIP_INFISICAL=1 bun run plan grant <email>` when running a
command against a database other than the default `dev` one. Without `SKIP_INFISICAL`,
Infisical overrides variables already set in the shell, so a plain inline override would
silently be ignored.

## First-time setup

Once per machine:

```bash
bun run setup      # reports which global tools are missing, and how to install them
infisical login
```

`scripts/setup-dev.sh` only checks — it never installs. After that, every command that needs
secrets fetches them itself; there is nothing to configure per app.

## Rules

- Never hand-write or hand-edit a `.env` file. Where one exists it was generated by
  `pull-env.sh` (or equivalent) and is gitignored.
- Adding a new Infisical folder means adding it to the `FOLDERS` list in
  `scripts/pull-env.sh` too, or its secrets go missing from generated files without any error.
- Never print secret values in logs, commits, or documentation.
